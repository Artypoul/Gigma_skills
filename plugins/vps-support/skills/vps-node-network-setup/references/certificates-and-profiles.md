# Сертификаты, сборки и фактический профиль

## Четыре разных проверки

| Контур | Что проверять | Чего он не доказывает |
|---|---|---|
| Панель → API ноды | Live TLS, pinned CA панели, SAN адреса/имени, срок, fingerprint; оба фактических порта | Доступность пользовательского VLESS |
| Пользователь → HTTPS панели | DNS, цепочка, имя/SNI, срок публичного сертификата | Работу нод |
| Нода → REALITY target | Доступность цели с самой ноды, DNS/семейство IP, TLS 1.3, нужные ALPN/имя | Успешную авторизацию REALITY клиента |
| Клиент → VLESS/REALITY | Актуальный полный профиль, поддержка ClientHello, реальный запрос через inbound | Стабильность всех маршрутов по одному успеху |

Определи, какой сертификат реально использует listener: конфигурация процесса/контейнера, mount и предъявляемый сертификат важнее имени файла. Self-signed/pinned management CA проверяется через доверие панели; публичное системное хранилище здесь может быть неподходящим. Не применяй `-k` как доказательство исправной цепочки.

Для публичного HTTPS пример проверки с разрешённого хоста:

```sh
timeout 8s openssl s_client -connect "$TLS_HOST:443" -servername "$TLS_HOST" \
  -verify_hostname "$TLS_HOST" -verify_return_error </dev/null
```

Для management TLS используй доверенный CA и `-verify_ip` либо `-verify_hostname` согласно SAN; при обязательном mTLS потребуется уже разрешённый клиентский сертификат. Не печатай ключи и не подставляй секреты в argv. Запиши UTC now, notBefore/notAfter, issuer, SAN и fingerprint; одного notAfter недостаточно.

При нераспознанном REALITY ClientHello клиент может увидеть поведение/сертификат fallback target. Ошибка x509 в таком случае требует проверки профиля и авторизации, а не немедленного перевыпуска сертификатов. Старый SNI после параллельной смены профиля — отдельное рассогласование, не доказательство первоначальной причины.

## Сравнение состояния

Сопоставь четыре источника: активная конфигурация/бинарник ноды; host/core в панели; вновь выданная подписка; фактическая конфигурация запущенного приложения. Обновление подписки пользователем не гарантирует, что твой тест взял актуальную версию после следующего изменения панели.

Без раскрытия значений секретов проверь:

- адрес и порт, активность записи ноды, outbound routing;
- transport, security, SNI, Host, path/serviceName, ALPN, fingerprint;
- совместимость public key и short ID с сервером, разрешение тестовой учётной записи;
- xHTTP mode, extra/XMUX и переиспользование соединений;
- клиентское ядро внутри приложения, точный серверный бинарник, хеш, build info, замены зависимостей;
- DNS, IPv4/IPv6, время системы и фактическую ревизию на протяжении теста.

Полные конфиги обычно содержат секреты. Запрашивай allowlist диагностических полей; совпадение секретных полей возвращай как bool. Не полагайся на regex-маскирование произвольного полного дампа.

Если один клиент получает `REALITY authentication failed`, а другой проходит при одинаковом пути/профиле, сравни TLS ClientHello и поддержку key shares по официальному коду **установленной** зависимости. Не делай правило «всегда откатывать Xray»: требования и исправления зависят от точной сборки. Не сохраняй полный пользовательский payload для такого сравнения.
