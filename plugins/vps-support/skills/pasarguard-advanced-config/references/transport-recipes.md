# Транспорты и маскировка

Источники и названия полей проверены 2026-11-09; документация Xray меняется. До применения сверь возможности установленного server/client core, панели и клиента. Примеры показывают схемы, а не гарантируют устойчивость в конкретной сети.

## Выбор по наблюдаемому сбою

| Наблюдение | Следующая проверка и область настройки |
| --- | --- |
| Нет соединения с адресом/портом | Проверь достижимость из нужной сети, DNS и IPv4/IPv6. Один таймаут не доказывает блокировку; смена SNI не создаёт недоступный сетевой маршрут. |
| Соединение доходит до TLS/REALITY и срывается | Сопоставь версии, SNI, target, ключевую пару и shortId без раскрытия секретов; затем сравни транспортные варианты. |
| Туннель работает, отдельный сервис возвращает отказ | Проверь фактический выходной IP, DNS, правила маршрутизации и ответ сервиса. Код 403 сам по себе не доказывает геоблокировку; маскировка входящего соединения не меняет ограничения аккаунта. |
| Подключение стабильно, но мала скорость или есть обрывы | Сними исходные показатели; меняй одну связанную группу параметров за шаг, проверяя результат и ухудшения. Не включай все маскировки одновременно. |

Для разделения направлений через уже имеющиеся выходы проверяй порядок routing rules, существование `outboundTag` и маршрут при отсутствии совпадений: обычные правила идут сверху вниз до первого совпадения, иначе используется первый outbound. Если настроен routing script, сначала изучи его. Источник: [Routing](https://xtls.github.io/en/config/routing.html). Настройка дополнительных серверов или внешних туннелей требует отдельной задачи.

## RAW + REALITY + Vision

- Для совместимых версий и клиента рассмотрите VLESS, `network: raw` (историческое имя TCP), `security: reality`, `flow: xtls-rprx-vision`. Flow и UUID должны согласовываться с сервером, существующие идентификаторы не менять. Vision доступен при TCP+TLS/REALITY; не переносить его автоматически на XHTTP. [VLESS](https://xtls.github.io/en/config/outbounds/vless.html), [transport](https://xtls.github.io/en/config/transport.html).
- Клиентский `serverName` должен входить в `serverNames`, соответствующих target и его реальному TLS-поведению; проверить target, сертификат/SAN и доступность с сервера. `shortId` — одно из серверных значений, чётная длина hex до 16 символов. Клиентский `password` (историческое имя `publicKey`) — производный публичный X25519-ключ, соответствующий серверному `privateKey`, НЕ сам `privateKey`. Никогда не помещай privateKey в клиент, подписку или чат и не запрашивай его у пользователя для аудита. Публичный материал также не публикуй открыто. В PG 5.5.1 publicKey вычисляется панелью: [core](https://github.com/PasarGuard/panel/blob/eba70d68eaa5a89e34ffebb47c8fd5ce054d0e43/app/core/xray.py#L273-L279), [подписка](https://github.com/PasarGuard/panel/blob/eba70d68eaa5a89e34ffebb47c8fd5ce054d0e43/app/subscription/xray.py#L354-L364). Сопоставляй обезличенно, пару проверяй на сервере только в разрешённом контексте; серверное `target` ранее называлось `dest`. Выбирай имена по установленной версии и её схеме, не заменяй их массово. Чужие ключи не копировать; target из примера использовать только после проверки соответствия окружению. [REALITY](https://xtls.github.io/en/config/transports/reality.html).
- Неавторизованный REALITY-трафик переадресуется на target; это может открыть нежелательное перенаправление. Оцени воздействие и поддерживаемые лимиты, не меняя прокси и сетевые службы без отдельного разрешения.
- `xtls-rprx-vision` перехватывает UDP 443; `xtls-rprx-vision-udp443` оставляет его доступным. Проверь QUIC и зависимые приложения, не предполагая одинаковое поведение всех клиентов.

Учитывай дополнительно VLESS `decryption` на сервере и соответствующий `encryption` в подписке: PG читает их из `inbound.settings`. При `decryption != none` панель требует заданный `encryption`; это отдельный механизм, его нельзя заменять значением `security: reality`. Flow из community `settings.clients[].flow` не заменяет проверку `inbound.settings.flow`, который PG использует для выдачи. Статический список чужих клиентов не импортируй в работающую панель. [PG VLESS](https://github.com/PasarGuard/panel/blob/eba70d68eaa5a89e34ffebb47c8fd5ce054d0e43/app/core/xray.py#L628).

Если используется ML-DSA-65 в REALITY, `mldsa65Seed` остаётся серверным секретом, а `mldsa65Verify` должен соответствовать ему. PG 5.5.1 отклоняет verify без seed; seed без verify допустим и не означает, что клиент проверяет эту подпись. Проверяй пару локально, не запрашивая seed в чате. Серверные ограничения `minClientVer`, `maxClientVer`, `maxTimeDiff`, `xver` и `limitFallbackUpload/Download` учитывай, когда они заданы или нужны для конкретного симптома. [PG REALITY](https://github.com/PasarGuard/panel/blob/eba70d68eaa5a89e34ffebb47c8fd5ce054d0e43/app/core/xray.py#L270), [схема Xray](https://github.com/XTLS/Xray-core/blob/676eaf66f8f05d4d558ee7a74b4736623d3feeb9/infra/conf/transport_security.go).

## XHTTP с TLS или REALITY

При добавлении нового XHTTP сначала проверь простой вариант без разделения направлений и дополнительных маскировок; существующий рабочий профиль сохрани. При аудите уже работающего split изучи его фактическую схему, не навязывая переход. `mode: auto` — кандидат только после проверки версии и принятия конфигурации клиентом и сервером.

| Слой | Что проверить и сопоставить |
| --- | --- |
| Server Core | `streamSettings.network`, `security`, `xhttpSettings.path`; security и серверные TLS/REALITY параметры на реально обслуживаемом inbound. |
| Host | Сопоставь экспорт с [картой полей PG 5.5.1](panel-mapping.md#практическая-карта-xhttp-551); Host сам по себе inbound не меняет. |
| Generated client | Фактические network/security/path/SNI и учётные данные соответствуют inbound и Host; проверить импорт и работу в конкретном клиенте. |

- Отдельно рассмотрите `network: xhttp` с `security: tls` или `reality`; соответствующие path, Host, SNI, TLS-сертификат/ключи и inbound должны согласовываться. По обычному TLS проверяй имя и действительность сертификата; не отключай проверку ради подключения. REALITY с XHTTP поддерживается только при наличии поддержки обеими версиями. [Transport](https://xtls.github.io/en/config/transport.html), [TLS](https://xtls.github.io/en/config/transports/tls.html).
- `fingerprint` имитирует ClientHello, а не всё сетевое поведение браузера. Для REALITY `unsafe` не поддержан; допустимые варианты и ALPN сверяй с установленной версией и клиентом. Не называй это невидимостью.
- Для разделения направлений `downloadSettings` — клиентский отдельный набор transport/security/address/port, который должен вести на согласованную серверную обработку и path. В официальном примере разделения `stream-one` неприменим, используется `stream-up`; путь размещения полей зависит от используемого формата и версии. В панели это ссылка на Host, а не вставка готового объекта: см. panel-mapping. Проверь фактический сгенерированный конфиг и обе стороны. [Пример XHTTP3](https://github.com/XTLS/Xray-examples/blob/main/VLESS-XHTTP3-Nginx/client.jsonc), [описание разделения](https://github.com/XTLS/Xray-core/discussions/4113/pages?before=DC_kwDOEo5NE84AuZg_).

Ограничения, подтверждённые [SplitHTTPConfig.Build в Xray v26.11.9](https://github.com/XTLS/Xray-core/blob/676eaf66f8f05d4d558ee7a74b4736623d3feeb9/infra/conf/transport_method.go), проверяй заново для установленного core:

- HTTP `Host` задаётся отдельным `xhttpSettings.host`, а не элементом `headers`.
- `uplinkHTTPMethod=GET` и `uplinkDataPlacement=cookie/header` требуют `mode=packet-up`.
- Положительные `xmux.maxConnections` и `xmux.maxConcurrency` одновременно запрещены.
- Пользовательские `sessionIDTable` и `sessionIDLength` проверяются совместно: недостаточное число комбинаций или неподходящая длина отвергаются.
- Числа и диапазоны padding проходят проверку core; не назначай ноль универсальным способом отключения.

`noSSEHeader`, `scMaxBufferedPosts`, `scStreamUpServerSecs`, `serverMaxHeaderBytes`, `h2Params` есть в этой схеме Xray, но отсутствуют в `XHttpSettings` Host PG 5.5.1. Не придумывай для них API-поля. Серверный параметр можно рассматривать в Core по его назначению; для клиентского нужен подтверждённый механизм изменения конечного профиля. Обычное добавление outbound в client template не меняет сгенерированный `proxy`.

## Дополнительные приёмы

- FinalMask, fragment и noise рассматривай опционально только при подтверждённой поддержке конкретных версий и как контролируемый A/B тест. Fragment меняет исходящий TCP; `tlshello` дробит ClientHello, размер и задержки влияют на результат. При нулевой задержке фрагменты могут оказаться в одном TCP-пакете; пустые TLS records нарушают RFC и поддерживаются не везде. Не копируй случайные значения как гарантию. [FinalMask](https://xtls.github.io/en/config/transports/finalmask.html).
- Выбирай маску по внешнему транспорту: в FinalMask `fragment` относится к `tcp`, `noise` — к `udp`. UDP приложения внутри TCP-туннеля не превращает внешний транспорт в UDP. Для слоёв, требующих согласования обеих сторон, сверяй тип, порядок и параметры пары client/server; не делай вывод о взаимозаменяемости масок по похожим названиям.
- Рассмотри DNS, IPv4/IPv6, routing и sniffing отдельно для обнаруженного симптома. Глобальные правила не менять без продуктового решения; измерять реальный путь и DNS. WARP, чужой SNI и CDN не являются универсальным обходом. Публичные UI templates сами по себе не маскируют транспорт.

## Выбор примеров

Используй [XTLS/Xray-examples](https://github.com/XTLS/Xray-examples), [chika0801/Xray-examples](https://github.com/chika0801/Xray-examples) и [lxhao61/integrated-examples](https://github.com/lxhao61/integrated-examples) как исходники конфигурационных идей. Для конкретного файла проверь дату и изменения, минимальную версию core и клиента, известные открытые issues и воспроизводимость пары client/server. Число звёзд не подтверждает безопасность; чужие скрипты не запускать и секреты не копировать.

Проверенные пары файлов и оговорки по переносу перечислены в [реестре источников](coverage-and-sources.md#исходные-репозитории-и-примеры). В частности, ключи с `#` в XHTTP3-примере — отключённые варианты, а несколько JSON-объектов подряд в файле lxhao61 — альтернативы, не единый импортируемый конфиг.
