# Проверка и откат

1. Зафиксируй server panel/node/core и версию приложения/core клиента, топологию, существующий профиль, операторов/сети, симптом и исходные измерения. Секреты из снимков исключи. Сверь значения inbound, Host, template и фактического профиля подписки; проверь серверную и клиентскую стороны.
   Для полного аудита заполни [перечень покрытия](coverage-and-sources.md): состояние каждой области, источник, наблюдаемый результат и неизвестное. «Полный» означает отсутствие нерассмотренных применимых областей, а не включение всех функций.
2. На точных версиях проверь candidate: `xray run -test -config <путь>` загружает и проверяет конфигурацию без запуска сервера ([команды Xray](https://xtls.github.io/en/document/command.html)). Успех не доказывает обработку панелью, применение каждого поля, совместимость импорта, маршрутизацию или соединение. Для составного конфига проверяй именно конечный собранный результат с действительными значениями в разрешённой среде; обезличенные метки из аудита в него не переносить. Не раскрывай секреты через `-dump` или логи.
3. Подготовь diff и возможный откат к проверенному прежнему состоянию; включи затронутых пользователей, риски, рестарт и rollback в пакет согласования. Отдельная тестовая группа/inbound (canary) — только по прямому актуальному согласию, с сохранением рабочего профиля.
4. При разрешённой проверке сравни исходный и candidate на реальных нужных клиентах и сетях: доля успешных подключений, задержка, скорость загрузки/отдачи, переподключение, IPv4/IPv6 и DNS; фиксируй время, оператора, версии и ошибки. Меняй одну связанную группу параметров за шаг и заранее определи приемлемое ухудшение скорости/задержки. Проверь полученный JSON, затем фактический профиль после импорта в приложение: формат URI или клиент могут потерять поля. Проверяй приложения, включая QUIC, если это важно. Отсутствие сбоя в одной сети не означает универсальной устойчивости или отсутствия утечек.
5. После согласованного изменения выполни read-back панели, сгенерированного профиля и состояния сервиса; сравни с согласованным diff. При неизвестном исходе записи остановись без повтора и выясни фактическое состояние чтением. Откат или рестарт выполняй в пределах точного актуального согласия на утверждённый пакет; повторное согласие на уже утверждённое действие не нужно. При неизвестном исходе или смене scope продолжение пакета прекращается.

Если нет подтверждённого клиентского и сетевого теста, сообщи «проект конфигурации», а не «работает в РФ». При несовместимости сохрани доказательства и предложи следующий минимальный тест, а не случайный набор настроек.

Для новых параметров подтверждай поддержку схемой или исходниками именно установленной версии. Например, [JSON loader Xray v26.3.27](https://github.com/XTLS/Xray-core/blob/v26.3.27/infra/conf/serial/loader.go) использует Go decoder без `DisallowUnknownFields`; [документация Go](https://pkg.go.dev/encoding/json#Decoder.DisallowUnknownFields) описывает отдельное включение ошибки на неизвестных полях. Следовательно, успешный `-test` сам по себе не исключает игнорирование неизвестного ключа. Это вывод из реализации, а не результат запуска этого core в данной среде.

При чтении профиля особо проверь: исчезновение `false`/`0`, legacy `max_split`/`maxSplit`, ссылки `dialerProxy` на существующие теги, наследование FinalMask, распределение XHTTP-полей между корнем и `extra`, выбор шаблона и настройки, потерянные при смене формата подписки. Сравни заявленную схему примера с фактической: комментарии и отключённые ключи не включают функцию.
