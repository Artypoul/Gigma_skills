# Расширенная настройка PasarGuard

Помогай улучшить уже установленную панель PasarGuard и её профили подключения:
сначала изучи фактическую конфигурацию, предложи конкретные параметры,
проверь совместимость и подготовь согласуемое изменение.
По умолчанию аудит, исследование и проектирование — только чтение.
Не устанавливай панель, БД или VPS и не меняй дизайн панели, ботов и тарифы.
Не предлагай принудительное обновление вместо анализа существующей версии.

Для полного аудита используй [перечень настроек и исходников](references/coverage-and-sources.md):
отметь для каждой области «проверено», «не применяется» или «неизвестно».
Для точечной задачи проходи только затронутые области и их зависимости.
Перечень привязан к PG 5.5.1; поддержку новых полей проверяй по версии,
а не по наличию названия в интерфейсе или свежем примере Xray.

## Маршрут

1. Уточни цель и наблюдаемый симптом; используй уже имеющиеся данные.
   Зафиксируй версию панели, ноды и серверного Xray, клиентское приложение и
   версию его core, топологию и участвующие сети/операторы, ошибку и время.
   Версия панели не доказывает версию Xray. Отделяй проверенные факты от гипотез.
2. Изучи действующий обезличенный пример server inbound, Host, клиентской
   подписки и при необходимости client template. Для сопоставления слоёв читай
   [panel-mapping.md](references/panel-mapping.md). Не публикуй и не передавай
   внешним генераторам секреты, UUID, ключи или полные приватные ссылки.
3. Подбирай параметры по [transport-recipes.md](references/transport-recipes.md).
   Начни с подходящего существующего транспорта; предложи альтернативы с
   ограничениями клиента, core и сети, а не универсальный набор значений.
4. Сверь настройки на серверной и клиентской сторонах, правила и логи на
   подходящей версии; план проверки и отката — в
   [verification.md](references/verification.md).
5. Покажи для каждого изменения: поле UI или JSON path → сейчас/предложение →
   причина и источник → сторона применения → тест → откат. Используй конкретный
   patch только по реальному обезличенному образцу и подтверждённому контракту.
   Если образца нет, составь карту изменений и укажи неизвестные поля;
   не придумывай рабочий API payload или поля интерфейса.

В обезличенном экспорте сохраняй структуру, типы и связи: одинаковые UUID,
домены и теги заменяются одинаковыми метками. Такой пример служит для аудита;
метки не должны попасть в действующую конфигурацию. При применении сохраняй
реальные секреты на их стороне, не запрашивая их в чате.

Не останавливай исследование из-за отсутствия всех исходных данных: сначала
используй доступные сведения и укажи границы. Спрашивай только данные,
необходимые для конкретного предлагаемого изменения или его проверки.
Для диагностики различай IP/allowlist, DNS, TLS, транспорт и приложение;
успех в одной сети не подтверждает работу во всех сетях или обход любого DPI.
Если туннель работает, а отдельный сервис отказывает в доступе, сначала
проверь маршрут и причину отказа сервиса; не считай это автоматически
проблемой маскировки подключения.

## Граница применения

Текущие UUID и ключи пользователей сохраняй. Чужие секреты и UUID не копируй.
Несекретные target, домен, путь и порт из примера переноси только после
проверки соответствия действующей схеме и обеим сторонам.
Новые ключи для нового профиля генерируй локально только при отдельно
разрешённом применении; не показывай секреты в отчёте.

Перед любой записью на сервере или в живой панели/API, а также рестартом и
откатом покажи конкретный diff, цель, затрагиваемые сущности, эффект, проверки
и возможный откат. Дождись прямого актуального согласия на конкретный пакет
действий в этой среде, включая предусмотренные рестарт и откат. Повторное
согласие на то же действие в пакете не требуется; неизвестный исход или
смена scope аннулируют продолжение. Read-only просьба
не является согласием. При неудачной записи или неизвестном исходе останови
мутации, прочитай состояние и доложи; не повторяй запись вслепую.

Для SSH используй только явно названные пользователем учётную запись и ключ;
не угадывай root, пользователей или ключи. При ошибке авторизации остановись.
Соблюдай действующие ограничения окружения; не обходи их и не требуй
отсутствующего скилла. Согласование не распространяется на другие окружения.

## Результат

Выдай конкретный проект конфигурации с источниками, неопределённостями и
планом A/B проверки: выбранный вариант, согласованные серверные и клиентские
параметры, минимальный diff либо карта полей, критерий успеха и откат.
Отдельно назови, что только предложено, что записано и что реально проверено.
Указывай проверенные версии и дату источников. Если
реальный клиент и сеть не проверены, статус — проект конфигурации, а не
«работает в РФ». Не заявляй об устранении утечек без измерения DNS и IPv6.
