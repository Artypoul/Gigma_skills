# Настройка ноды и панели PasarGuard

Для владельца или уполномоченного оператора. При переходе из расследования возьми его карточку и верни результат на тот же шаг. При прямом вызове закончи в текущем обращении. Сохраняй ограничения по хостам, доступу и месту проведения проб. [Общий контракт маршрутизации](../../reference/vps-routing.md)

Если обращается подписчик без операторского доступа, верни его в [пользовательскую диагностику](../vps-troubleshoot/SKILL.md). При поручении «проверить на сервере» используй журналы, конфиг и локальный служебный запрос на разрешённой ноде. Пробы с компьютера клиента требуют отдельной задачи.

**Перед подключением к PG Артёма** открой локальный ранбук `C:\Users\Art\.ssh\pg\PG-RUNBOOK.md` (на его Windows-машине — `%USERPROFILE%\.ssh\pg\PG-RUNBOOK.md`). В нём есть реквизиты: читай только нужный раздел, не выводи файл целиком в журнал или чат.

1. Выбери машину по роли и имени. Для ноды сверь её ID и назначение в текущей панели PG. Адрес в подписке ведёт клиента к сервису, адрес управления нужен панели для связи с pg-node. Для SSH используй адрес ОС, сверенный с актуальным инвентарём VPS или подтверждённый владельцем для этой машины.
2. IP и команды ранбука отражают состояние на указанную дату. Перед **каждым SSH-подключением** сверь выбранный IP, порт, пользователя и ключ с действующей записью. Если источники расходятся или сверить адрес не удалось, остановись до подключения и уточни маршрут. При новом адресе или изменившемся ключе сервера сверь отпечаток по доверенному каналу.
3. После входа сравни `hostname` с ожидаемым именем и `id -un` с согласованным пользователем. При расхождении заверши сеанс. Если локальный ранбук недоступен, запроси у владельца маршрут к нужной машине.

## Определи объект изменения

Составь одну строку на каждый профиль: ID ноды → адрес управления и порты → ID назначенного core-конфига → тег входа Xray → ID хоста подписки → клиентский адрес, порт и транспорт. У нескольких адресов может быть один процесс. Одинаковые названия у разных ID не объединяй. Сопоставляй архив с работающей системой по ID, адресу, времени и версии. Отдельно отметь, что взято из БД, что прочитано у службы и что выдано подписчику.

Для настройки экземпляра панели, полномочий, глобальных параметров или полного аудита полей перейди в [настройку панели PasarGuard](../vps-panel-setup/SKILL.md). Передай ID и уже проверенные данные. Когда подзадача завершена, продолжи проверку самой ноды с сохранённого шага.

При пересоздании ноды или смене IP до первой записи выполни раздел «Приёмка смены адреса или пересоздания ноды» в [скилле панели](../vps-panel-setup/SKILL.md). Передай все затронутые Host ID и ожидаемые клиентские адреса. В отчёте раздели связь панели с pg-node и доступ к каждому профилю из подписки с указанной точки проверки. Если клиентский путь остался открытым вопросом, верни результат восстановления со статусом `partial`.

## Xray от Jolymmiles: выбор версии и расследование ошибки

1. **Установи происхождение сборки.** На ноде найди PID Xray нужного слушателя и исполняемый файл через `/proc/<PID>/exe`. Сопоставь полный вывод `version` и SHA-256 с артефактом под ОС и архитектуру ноды. Панель может показать укороченную версию. Для Jolymmiles ищи обновление в [релизах автора](https://github.com/Jolymmiles/Xray-core/releases); проверь тег, дату, признак prerelease и digest. Переход между Jolymmiles и XTLS — отдельное решение владельца. Установленный тег и кандидат фиксируй при каждом разборе.
2. **Ищи по наблюдаемому симптому.** Запиши версии клиента и сервера, транспорт, точную ошибку, ожидаемый результат и шаг воспроизведения. Ищи компонент и текст ошибки в [открытых и закрытых Issues](https://github.com/Jolymmiles/Xray-core/issues) и [PR](https://github.com/Jolymmiles/Xray-core/pulls). По [описанию отличий форка](https://github.com/Jolymmiles/Xray-core/blob/3b2591c6c55d2d7b678ce5642011da1387843179/docs/FORK.md) найди настройку и соответствующий тест; открой этот файл также на теге исследуемой версии. Для найденного исправления проверь условия проявления, merge-коммит, его вхождение в тег кандидата и раздел совместимости релиза. Закрытый issue или зелёный CI сами по себе не подтверждают причину на этой ноде.
3. **Воспроизведи и сравни.** Из [формы сообщения об ошибке](https://github.com/Jolymmiles/Xray-core/blob/3b2591c6c55d2d7b678ce5642011da1387843179/.github/ISSUE_TEMPLATE/bug_report.yml) возьми парные конфиги клиента и сервера, два журнала и точные шаги. Для стенда подставь тестовые секреты, сохрани все зависимости профиля и сними логи в одном окне UTC. Проверь исходную сборку и кандидат с тем же клиентом, маршрутом и конфигом; меняй один фактор. Если дефект совпадает только по описанию, обозначь его гипотезой. Пример из [релиза v26.11.1-1424](https://github.com/Jolymmiles/Xray-core/releases/tag/v26.11.1-1424): старые номера полей XHTTP затронули **protobuf**; для JSON этот конкретный дефект неприменим. Установи фактический формат данных до выбора исправления.
4. **Выбери проверку под жалобу.** Для обрыва при reload воспроизведи переподключение на стенде, для сбоя после длительной работы — серию запросов достаточной длительности, для падения скорости — сравни одинаковую нагрузку после прогрева. Запиши условия, результат до и после и оставшиеся ограничения. Источники подхода — [правила тестирования автора](https://github.com/Jolymmiles/Xray-core/blob/3b2591c6c55d2d7b678ce5642011da1387843179/AGENTS.md) и [проверки перед выпуском](https://github.com/Jolymmiles/Xray-core/blob/3b2591c6c55d2d7b678ce5642011da1387843179/.github/workflows/pre-release-validation.yml). Нагрузочные проверки проводи на стенде. Для обновления production подбери обратимую операцию, проверь кандидат через `run -test` и получи разрешение. После применения проверь версию живого процесса и каждый затронутый профиль из свежей подписки с внешней разрешённой точки по [порядку проверки каждого профиля](../vps-panel-setup/SKILL.md#profile-verification). В отчёте раздели результаты автора и собственные наблюдения.

## Подключить ноду и опубликовать профиль

1. **На ноде.** Определи способ запуска (systemd или контейнер), версию pg-node, путь к исполняемому Xray и его ресурсам. Для новой ноды подбери способ установки по документации именно этой версии. Подготовь адрес прослушивания, протокол и порты управления, ключ API, сертификат с SAN адреса/имени управления, путь к сертификату и соответствующему приватному ключу. Проверь доступность файлов пользователю службы. Порты управления разрешай от согласованного адреса панели, клиентские порты — по схеме сервиса. Перед применением покажи изменения службы, firewall и ожидаемое влияние. [Параметры pg-node](https://docs.pasarguard.org/en/node/configuration/)
2. **В панели.** Заведи или выбери запись нужной ноды. Сопоставь адрес, порты, протокол, ключ API и доверенный сертификат с настройками службы. Назначь core-конфиг по ID. В нём задай входы, уникальные теги, адреса прослушивания, порты, REALITY, исходящие соединения и правила маршрутизации. Проверь ссылки правил на существующие теги, доступ к файлам geodata и занятость портов. При нескольких IP отдельно проверь исходящий адрес и обратный маршрут.
3. **В профиле панели.** Свяжи хост с нужным входом, назначь адреса для клиента, транспорт и разрешённые группы. Установи, какие поля заданы явно, а какие наследуются. Проверь теги по **всем** core-конфигам, включая неназначенные. В версиях с общим индексом повтор тега может подменить наследуемый путь. Выясни приоритет по коду установленной панели и фактической выдаче.
4. **Перед записью.** Проверь контракт API установленной версии: адрес операции, обязательные поля, частичное или полное обновление, автоматическое переподключение. Зафиксируй предыдущее состояние в разрешённом защищённом месте. Покажи точный объект, поля, эффект и обратную операцию без секретов. После разрешения перечитай объект и остановись при конкурентном изменении. При неизвестном результате записи сначала проверь состояние чтением.
5. **После применения.** Отдельно проверь сохранение записи, получение конфигурации нодой, запуск Xray и выдачу профиля. Для действующего сервиса сравни до/после все поля затронутых объектов и контрольные профили. При выборе адреса из пула проверяй принадлежность разрешённому списку. Пользовательский запрос через профиль выполняй лишь в разрешённой среде. Отмечай пропущенную проверку явно.

**Пример для существующей панели.** В PasarGuard v5.5.1 хост подписки читается через `GET /api/host/{host_id}`. При явно согласованном исправлении одного поля `PUT /api/host/{host_id}` принимает описание хоста целиком. Сохрани остальные поля из свежего чтения, включая тег входа и настройки транспорта. Запись управляющей ноды меняется отдельно через `PUT /api/node/{node_id}` и может инициировать переподключение. Перед использованием на другой сборке проверь её схему и обработчик. Успешный HTTP-ответ проверь повторным чтением и фактической выдачей.

## Проверить работающую ноду без изменений

| Что выяснить | Как получить доказательство |
|---|---|
| Кто слушает каждый порт | На ноде выполни `ss -lntp`. Сопоставь PID с `docker top <контейнер> -eo pid,comm` или `systemctl show <unit> -p MainPID`. Порты управления и клиентские порты проверяй отдельно. |
| Какой ключ принят | С разрешённым доступом выбери только `API_KEY` из окружения PID нужного слушателя. Сравни в памяти с панелью и, при необходимости, датированным снимком. При сравнении на разных машинах используй HMAC с общей одноразовой случайной солью. Выведи только результаты совпадения. Подтверди ключ авторизованным локальным запросом чтения, например gRPC `GetBaseInfo`, если метод есть в установленной версии. |
| Какому сертификату доверяет панель | Сравни сертификат из записи панели, файл, доступный процессу через его mount, и сертификат слушателя. Проверь срок, SAN и цепочку с доверенным CA панели. Укажи, проверялся ли живой слушатель. Проверка управления и проверка REALITY относятся к разным соединениям. |
| Запущен ли Xray | Сопоставь поле `started` ответа ноды, процесс Xray, его версию и слушающие входы. Статус контейнера или успешное чтение версии pg-node подтверждают только работу службы управления. |
| Почему запуск не состоялся | Сведи в UTC сообщения панели об отправке `Start`, результат RPC, журналы pg-node и Xray с момента старта контейнера. Для чтения подойдут `docker logs --timestamps --since <UTC> <контейнер>` и `journalctl --utc -u <unit> --since <время>`. Фильтруй чувствительные данные до вывода. Различай попытку отправки, приём на ноде, ошибку разбора и завершение уже запущенного ядра. При тайм-ауте одной стороны факт приёма остаётся открытым. |
| Готов ли назначенный конфиг | Сравни сохранённый JSON с тем, что сериализует панель для этой ноды. Если аккаунты передаются в `Start` отдельно, проверь число пригодных записей и группы без вывода UUID. Если нужен тест синтаксиса, используй штатный режим `run -test` той же сборки в изолированных условиях с нужными ресурсами. Его успех подтверждает разбор, для проверки запуска нужны процесс и порты. |

Секреты из `.env`, полного `docker inspect`, подписки и журналов не выводи. Значение из файла запуска может расходиться с окружением живого процесса. После отказа в SSH зафиксируй точный хост и учётную запись, останови попытки до уточнения доступа. Сброс счётчиков, синхронизация пользователей, reconnect, перезапуск и смена ключа требуют разрешения на соответствующую операцию.

### Когда контейнер работает, а Xray останавливается

Сверяй API-ключ **работающего процесса** с записью именно этой ноды в PG. Снимок или файл .env не доказывают, что процесс получил это значение. Сравнивай в памяти, выводи только совпадение. Сверь доверенный сертификат панели с фактически предъявленным на каждом служебном порту, проверь срок, SAN нового IP и соответствие приватному ключу. Проверяй служебный запрос чтения (например, GetBaseInfo) на подтверждённом TLS-соединении. Локальный успех подтверждает ключ и службу; путь от панели проверяется отдельно.

Разделяй роли pg-node, pg-node-service и Xray. В режиме Docker host порты слушаются прямо на машине. Перезапуск контейнера ещё не означает запуск ядра: проверь ответ службы, PID и клиентские порты. Сопоставь по времени Start, появление слушателей, keepalive timeout, остановку Xray и статус в PG. Если авторизован локальный запуск, используй текущий сгенерированный панелью конфиг с пользователями и **тем же** keepalive; одноразовый успешный Start не восстанавливает управление. Не обходи потерю связи отключением таймера. До ротации ключей, замены транспорта или переустановки раздели сбой TCP, TLS, авторизации и самого ядра.

У pg-node и Xray разные издатели и версии. Ссылки на релизы, тег, SHA-256 ядра и digest контейнера сверяй раздельно. Выдавай рекомендацию за авторскую только при наличии источника для этой версии. Подобранные SNI, Host, путь и gRPC serviceName должны совпасть в панели, ядре и профиле, а форковые параметры транспорта не заменяют служебный keepalive.

## Проверить предложенный домен маскировки с ноды

1. Из назначенного core и его входа возьми адрес и порт цели, отдельно — предполагаемый клиентский SNI. Для прямого REALITY с внешней TLS-целью проверяй именно эту пару. При собственном сайте за локальным nginx проследи путь до его фактического слушателя. Если TLS завершается на внешнем прокси, проверь его сертификат и правила проксирования по соответствующей схеме. Выбор примера и принадлежность полей описаны в [инструкции панели](../vps-panel-setup/SKILL.md).
2. Для внешней TLS-цели из сетевого пространства Xray проверь фактический маршрут и TLS. В примере ниже переменная TARGET содержит адрес цели с портом (IPv6 в квадратных скобках), SNI — доменное имя. Выполни одну пробу, если исходящие запросы разрешены. При отсутствии инструмента укажи, какая проверка осталась открытой.

   ```sh
   openssl s_client -connect "$TARGET" -servername "$SNI" -verify_hostname "$SNI" \
     -verify_return_error -tls1_3 -alpn h2 </dev/null
   ```

   Проверь установление TLS 1.3, успешную проверку цепочки и имени и фактически выбранный ALPN h2 для этой схемы. Запиши точку проверки, UTC и результат без полного вывода. Если у службы свой DNS, исходящий IP или прокси, учти их при пробе и укажи различия. Успешный TLS до цели подтверждает только этот участок.
3. Если TLS к цели успешен, сверь SNI, ключ, short ID и транспорт по разделу ниже. Для новой пары REALITY используй штатный `xray x25519` своей версии только при согласованной настройке; приватную часть сразу помести в защищённую серверную конфигурацию без вывода в чат или журнал. При проверке действующего входа сравни публичную часть с подпиской без ротации ключа. Для проверки управления pg-node используй отдельную строку про API-ключ выше.
4. Если Xray отсутствует или `started=false`, вернись к журналам `Start`. Для отчёта отдели доступность сайта с ноды, факт запуска входа и успешность соединения через конкретный профиль. Для каждого приведи отдельное наблюдение либо точный недостающий доступ.

## Сверить Xray с тем, что выдаёт панель

Сопоставь оба представления подписки, если панель их поддерживает: ссылку VLESS и готовый JSON Xray. Сверяй с назначенным **серверным** конфигом и явными переопределениями хоста. Сравнение с рабочей нодой — дополнительный контроль.

- **REALITY:** порт, транспорт, цель `target`/`dest` по версии, клиентский SNI в `serverNames`, публичный ключ от соответствующего приватного ключа, допустимый `shortId`, fingerprint и flow. Секретные поля сравнивай на месте.
- **xHTTP:** сравни фактические `path` и Host, режим, дополнительные параметры передачи и отдельные адреса загрузки, если заданы. У автора схема с собственным сайтом использует внешний REALITY-вход, fallback во внутренний xHTTP и локальный nginx. Перенос такой схемы требует учесть все три компонента. Для простого входа используй применимый инвариант — совпадение пути — без копирования чужого домена, ключей или nginx. [Сервер, клиент и nginx у chika0801](https://github.com/chika0801/Xray-examples/tree/383483096aad1e2979d46af17210fe4637438cf5/VLESS-XHTTP-REALITY/steal_oneself)
- **gRPC:** сверь `serviceName`, SNI, адрес, порт, режим клиента и поддержку HTTP/2. Учитывай значения по умолчанию установленных версий. Разницу, которая воспроизводится и на рабочем контроле, сначала проверь отдельно. [Парные конфиги gRPC у chika0801](https://github.com/chika0801/Xray-examples/tree/383483096aad1e2979d46af17210fe4637438cf5/VLESS-gRPC-REALITY)

**Пример решения.** У хоста SNI верен, но в двух форматах подписки путь совпал с неназначенным конфигом, использующим тот же тег. Доказан дефект выдачи. Узкая правка — явный путь у одного хоста, затем независимое чтение панели и двух форматов подписки. Если при этом pg-node сообщает `started=false`, веди отдельную ветку запуска. Успех правки подписки не подтверждает запуск Xray.

В отчёте укажи ID, версию и время, доказанную границу отказа, использованные источники, точечное исправление и способ проверить результат. Если серверного свидетельства нет, назови конкретно, какое чтение его даст. Верни результат вызывающему расследованию с того же шага.
