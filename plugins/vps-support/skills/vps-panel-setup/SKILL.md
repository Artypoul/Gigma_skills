# Панель PasarGuard

Для владельца или оператора панели. При прямом вызове сначала определи задачу: новая установка, аудит существующей панели или правка одного объекта. При переходе из расследования сохрани ID объектов, время, разрешения и шаг возврата. Вопросы о ключе запущенного pg-node, состоянии Xray и журналах самой ноды передавай в [настройку ноды](../vps-node-panel-setup/SKILL.md) по [правилам маршрутизации](../../reference/vps-routing.md). Если этот скилл уже вызвал тебя, верни результат в его сохранённый шаг.

**Перед подключением к PG Артёма** открой локальный ранбук `C:\Users\Art\.ssh\pg\PG-RUNBOOK.md` (на его Windows-машине — `%USERPROFILE%\.ssh\pg\PG-RUNBOOK.md`). В нём есть реквизиты: читай только нужный раздел, не выводи файл целиком в журнал или чат.

1. Выбери машину по роли и имени. Для ноды сверь её ID и назначение в текущей панели PG. Адрес в подписке ведёт клиента к сервису, адрес управления нужен панели для связи с pg-node. Для SSH используй адрес ОС, сверенный с актуальным инвентарём VPS или подтверждённый владельцем для этой машины.
2. IP и команды ранбука отражают состояние на указанную дату. Перед **каждым SSH-подключением** сверь выбранный IP, порт, пользователя и ключ с действующей записью. Если источники расходятся или сверить адрес не удалось, остановись до подключения и уточни маршрут. При новом адресе или изменившемся ключе сервера сверь отпечаток по доверенному каналу.
3. После входа сравни `hostname` с ожидаемым именем и `id -un` с согласованным пользователем. При расхождении заверши сеанс. Если локальный ранбук недоступен, запроси у владельца маршрут к нужной машине.

## Приёмка смены адреса или пересоздания ноды

1. **До согласования записи** составь таблицу: ID ноды и адрес управления → ID core и тег входа → все ID из раздела «Хосты» с этим тегом → клиентские адреса, порты и транспорт. Учти общие теги, отключённые записи, пул адресов, домен и внешний прокси. Установи, каким профилям и нодам служит каждый Host. Для каждого активного профиля запиши ожидаемый клиентский адрес после работ и основание выбора.
2. В PG v5.5.1 изменение `Node.address` переключает связь панели с pg-node. В каждой карточке с явно заданным `Host.address` сохраняется собственный список адресов подписки. Для обычных VLESS-профилей `Host.address` не наследуется из `Node.address` или core и при отсутствии остаётся пустым; порт, SNI и path могут наследоваться там, где применимы. [Сборка профиля](https://github.com/PasarGuard/panel/blob/eba70d68eaa5a89e34ffebb47c8fd5ce054d0e43/app/core/hosts.py#L146-L289). Проверь **оба раздела**. Рабочий клиентский домен/CDN или отдельный IP может остаться прежним. Если старый адрес недоступен, проверь кандидат на клиентском порту и включи конкретные ID хостов, изменения, влияние на подписчиков и откат в тот же план согласования, что и правку ноды. Разрешение только на запись ноды оставляет правку Host отдельным шагом.
3. После записи перечитай каждый Host и сравни все поля и контрольные хосты. Проверь сериализацию полной модели перед PUT: например, на v5.5.1 явный `alpn: []` и пропуск поля могут сохраниться по-разному. Получи свежую выдачу по разрешённой подписке в форматах клиента (например, VLESS и JSON Xray). Из каждого профиля извлеки адрес, порт, транспорт и SNI; сравни с таблицей. Для пула проверь состав в панели и принадлежность выданного адреса. Значения секретов оставь в памяти.
4. Для задачи «восстановить подключение» проверь каждый затронутый транспорт по адресу **из подписки** с разрешённой точки вне целевой ноды, сохранив зависимости профиля (например, XHTTP dialer). Запиши точку проверки и результат запроса через профиль. TCP и TLS проверяют только свои участки. При жалобе из конкретной сети отдельно укажи, проверена ли она. Если доступна только сама нода, недоступный адрес всё ещё выдаётся или требуется разрешение исправить Host, результат восстановления — `partial`. Укажи профиль и недостающее действие. Статус `connected` и локальный запрос подтверждают только управление и работу на самой машине.

Если PG выдаёт профиль для Jolymmiles, сверь версию запущенного Xray и формат, который фактически получает ядро или клиент. При ошибке импорта, старта или несовместимости параметров пройди [разбор релизов и ошибок Jolymmiles](../vps-node-panel-setup/SKILL.md#jolymmiles), затем сравни сохранённый core, поля Host и реальную выдачу. Для проверки подобранного исправления используй критерии приёмки выше.

### Один IP меняется в нескольких местах

В отдельные колонки внеси SSH-адрес ОС, адрес управления Node и оба служебных порта, адрес каждого Host, а также исходящий IP в `freedom.sendThrough` (обычно тег `DIRECT`). Проверь маршрут каждого входа до этого выхода. Новый адрес должен быть назначен интерфейсу. На машине с несколькими IP проверь фактически выбранный источник: изменение Host меняет вход клиента, но само по себе не задаёт выход. Перед изменением core получи список всех нод, которым он назначен. Настройки чужой ноды, ключи и адреса не копируй.

До записи сверь с панели прямой TCP и TLS по новому адресу, проверь SAN и доверенный сертификат. Если сертификат выписан на старый IP, согласуй его замену, использование прежнего приватного ключа и перечитывание обеими службами. Сохрани закрытую копию изменяемых объектов. При таймауте PUT сначала выполни GET по тому же ID: сервер мог сохранить изменение до истечения времени ответа. После каждого Host сравни всю запись с исходной, включая нормализацию `alpn` из `[]` в `null`; смысл для клиента проверяй по экспорту и реальному запросу.

Закрой задачу по свежей подписке: **каждый** профиль отдельно, входной IP и порт, HTTPS-ответ и фактический выходной IP. Повтори через две минуты и после установленного интервала keepalive, если он длиннее. Одновременно перечитай статус узла в панели и слушатели на ноде. Если изменился адрес в подписке, укажи владельцу в отчёте, что клиенту нужно обновить подписку.

## Установить границы версии и инстанса

Канон — [PasarGuard/panel](https://github.com/PasarGuard/panel) и [документация проекта](https://docs.pasarguard.org/ru/). Ниже ссылки на проверенную редакцию тега `v5.5.1`. Для другой версии сверяй соответствующий тег, а для собственной сборки — обработчики внутри установленного образа. Запиши digest образа, команду запуска, роль процесса и версию схемы БД, если она доступна. Проследи реальный путь от домена панели через reverse proxy до TCP-порта или Unix-сокета, контейнера и выбранной БД. Это исключает работу с тестовым экземпляром на том же сервере. Секреты и полные URL подключения в отчёт не переносятся.

## Когда просят настроить маскировку одного профиля

1. **Найди действующий вход.** Прочитай ноду по ID, затем назначенный ей core по ID. В списке `inbounds` найди точный `tag` из записи хоста. Выпиши протокол, `streamSettings.network` и `streamSettings.security`. Для входа за reverse proxy установи, где фактически завершается TLS. При нескольких совпадениях тега проверь их влияние на подписку перед выбором правки.
2. **Выбери подходящий образец.** Для прямого VLESS + XHTTP + REALITY с внешним сайтом открой вместе [сервер XTLS](https://github.com/XTLS/Xray-examples/blob/167cded1a33ac7b0ce76fcf00ea2d8fb0604e927/VLESS-XHTTP-Reality/minimal-steal_others/server.jsonc) и [клиент XTLS](https://github.com/XTLS/Xray-examples/blob/167cded1a33ac7b0ce76fcf00ea2d8fb0604e927/VLESS-XHTTP-Reality/minimal-steal_others/client.jsonc). Серверный пример задаёт структуру входа, клиентский помогает проверить выдачу. Для обычного TLS найди сертификат и место завершения TLS. Для REALITY с собственным сайтом и fallback используй схему с nginx из [инструкции ноды](../vps-node-panel-setup/SKILL.md).
3. **Определи владельца каждого поля.** В core лежат REALITY `target` (в старых версиях `dest`), допустимые `serverNames`, закрытый ключ и `shortIds`. В профиле Host проверь переопределения для подписки. Клиентский SNI выбирается из допустимых имён, `pbk` соответствует закрытому ключу, `sid` входит в разрешённый список. HTTP Host, путь и режим XHTTP сверяй отдельно с транспортом и правилами прокси. Адрес подключения клиента бери из схемы ноды или её входного прокси. [Правила Core](https://docs.pasarguard.org/en/panel/core/) · [Правила Host](https://docs.pasarguard.org/en/panel/host/)
4. **Подготовь минимальное изменение.** Если вход уже принимает нужные значения, а профиль выдаёт другие, подготовь правку одного Host. Если меняется серверная цель, перечисли ноды и профили с этим core и сначала проверь цель с нужной ноды. Для нового входа перенеси только нужные поля JSONC, сохрани уникальный тег и действующие outbounds и правила PG. Пользователей привязывай штатным способом панели. Закрытый ключ и short ID для нового развёртывания создавай в защищённой среде; при аудите существующего сохрани действующие значения.
5. **Покажи оператору результат до применения.** Назови объект и поля, ожидаемые значения на ноде и в подписке, затронутые профили и способ вернуть прежнее состояние. После согласования следуй разделу «Прочитать и безопасно изменить». Отдельно запиши три результата: что сохранено в PG, что запущено на ноде, что получил тестовый профиль.

## Настройка с нуля

1. Выбери закреплённую версию панели и поддерживаемый тип БД. Сверь образ, env-файл, сеть и постоянные тома с compose этой версии. Для действующей БД проверь резервную копию и возможность восстановления до согласования миграций. Внешний доступ к БД для работы панели обычно не нужен. [Compose](https://github.com/PasarGuard/panel/blob/eba70d68eaa5a89e34ffebb47c8fd5ce054d0e43/docker-compose.yml) · [Переменные окружения](https://github.com/PasarGuard/panel/blob/eba70d68eaa5a89e34ffebb47c8fd5ce054d0e43/.env.example)
2. Задай слушатель Uvicorn: адрес и порт либо Unix-сокет, доступный reverse proxy. Определи, где завершается HTTPS, кому доступны файлы сертификата и кому разрешено передавать proxy headers. Сверь путь dashboard, публичный origin и базовый путь подписки. Проверь публичное имя и upstream отдельно.
3. Выбери роль панели и количество workers. При разнесении ролей сверь настройки NATS, доставки команд нодам и работы планировщика по версии. Заведи владельца штатным способом для новой установки; в существующей используй разрешённую учётную запись с правами на нужные объекты. Доступ к хосту, токен администратора панели и ключ связи с нодой дают разные полномочия. [Настройки процесса](https://github.com/PasarGuard/panel/blob/eba70d68eaa5a89e34ffebb47c8fd5ce054d0e43/config.py) · [Первоначальная настройка владельца](https://github.com/PasarGuard/panel/blob/eba70d68eaa5a89e34ffebb47c8fd5ce054d0e43/app/routers/setup.py)
4. Подготовь core-конфиг и теги входов, затем зарегистрируй ноду с её адресом управления, доверенным CA, ключом и ID этого конфига. Создай хосты подписки для нужных входов, свяжи входы с разрешённой группой и проверь назначение группы тестовой учётной записи. Записывай выданные ID. Перед повтором прерванного создания проверь, какие объекты уже существуют.
5. Настрой форматы, публичный URL и правила выдачи подписки. Проверь их штатным ограниченным чтением с согласованной тестовой записью. Учитывай, что получение подписки может отражаться в журналах и учёте устройства. Проверяй запуск ноды, сохранение объектов панели и фактическую выдачу раздельно.

## Проверка доступности и HTTPS

Авторы поддерживают Caddy или Nginx с подключением к панели через localhost либо Unix-сокет. При Unix-сокете в контейнерах проверь доступ обоих контейнеров к файлу сокета; проверь настройку доверенных proxy headers. Доступность HTTPS подтверждай с проверкой доверия и имени сертификата. [Запуск панели](https://github.com/PasarGuard/panel/blob/eba70d68eaa5a89e34ffebb47c8fd5ce054d0e43/main.py#L119-L146)

В v5.5.1 `/health` возвращает статический `{"status":"ok"}` и не проверяет БД, ноды или клиентский путь. Для мониторинга проверяй endpoint из фактических точек доступа. Клиентские reset сопоставляй по времени, IP и User-Agent с другими свидетельствами; один reset не устанавливает причину. [Обработчик health](https://github.com/PasarGuard/panel/blob/eba70d68eaa5a89e34ffebb47c8fd5ce054d0e43/app/routers/home.py#L16-L18)

## Резервное копирование

Сначала проверь схему и версию установленного скрипта управления: сайт документации может расходиться с кодом. В scripts на ревизии `2da3ab1fa5ac474505fd91cdd9cae23b4b1b2cda` каталог копий — `APP_DIR/backup`, а после успешного создания предыдущие архивы backup удаляются; при аудите проверь хранение нескольких поколений вне сервера, при настройке включи это в согласованный план. [Каталог](https://github.com/PasarGuard/scripts/blob/2da3ab1fa5ac474505fd91cdd9cae23b4b1b2cda/lib/pasarguard-backup.sh#L1248-L1250) · [Удаление прежних архивов](https://github.com/PasarGuard/scripts/blob/2da3ab1fa5ac474505fd91cdd9cae23b4b1b2cda/lib/pasarguard-backup.sh#L2009-L2015) · [Документация](https://github.com/PasarGuard/scripts/blob/2da3ab1fa5ac474505fd91cdd9cae23b4b1b2cda/docs/backup-and-restore.md)

Если используются внешняя PostgreSQL или тома сертификатов Caddy, проверь их наличие в архиве; при отсутствии включи отдельную копию в согласованный план. `restore --check` распаковывает архив во временный каталог и затем удаляет его: запуск на сервере требует разрешения на эти файловые операции, хотя данные в БД не импортируются и службы не останавливаются. Проверяются структура, контрольные суммы при наличии инвентаря, завершённость SQL-дампа и целостность SQLite, но не запуск восстановленной системы. Пробное восстановление проводи отдельно: сначала на исходных версиях, затем планируй обновление.

## Полный аудит уже работающей панели

Начни с **перечня полей установленной версии**. Для окружения возьми определения настроек, для API — схему чтения и записи, для произвольного JSON ядра — все пути в реальном документе. Раскрой вложенные объекты и списки. Не считай проверенным раздел по нескольким знакомым полям. Используй ведомость:

| Объект / ID / путь поля | Где задано и откуда наследуется | Что сохранено | Что реально применено или выдано | Итог |
|---|---|---|---|---|
| Хост → тег → путь xHTTP | Явное поле либо настройка входа | Сравнение по ID core | Путь из VLESS и JSON Xray | Совпало / отличается / недоступно / неприменимо с причиной |

Для секретов сохраняй только наличие и результат защищённого сравнения. При неполном доступе перечисли конкретные непрочитанные поля или источники. Отличай `null`, отсутствие поля, пустую коллекцию и значение по умолчанию. Для правил маршрутизации, форматов и приоритетов сохраняй порядок; для множества разрешённых адресов сравнивай состав. Отдельно учитывай ревизии, нормализацию API и вычисляемые счётчики.

| Область | Что сверять |

Для отключённых интеграций отметь состояние без отправки проверочного сообщения. ## Прочитать и безопасно изменить

В v5.5.1 `GET /api/settings` возвращает настройки приложения с правом `settings.read`, а `GET /api/settings/general` — только общую часть. Для объекта используй `GET /api/core/{core_id}`, `GET /api/node/{node_id}`, `GET /api/host/{host_id}` или `GET /api/group/{group_id}`. При инвентаризации всех объектов учти постраничность и форму ответа каждого списка. Не выводи сырые ответы, токены, приватные ключи, персональные данные и ссылки подписок. [Обработчики официального API](https://github.com/PasarGuard/panel/tree/eba70d68eaa5a89e34ffebb47c8fd5ce054d0e43/app/routers)

Для правки покажи ID, изменяемые поля, охват по связанным нодам/хостам, ожидаемый побочный эффект и обратную операцию. Получи разрешение на конкретную среду и изменение. Повторно прочти исходное состояние перед записью. Для `PUT /api/settings` проверь полную модель настроек и обработку пропущенных полей. Для `PUT /api/host/{host_id}` сохрани прочие поля, необходимые полной модели хоста. Для `PUT /api/node/{node_id}` проверь семантику частичного изменения и фонового переподключения. Смена общего core может затронуть несколько нод. Reset, sync, reconnect и рестарт выполняй только в согласованном объёме. [Обновление настроек](https://github.com/PasarGuard/panel/blob/eba70d68eaa5a89e34ffebb47c8fd5ce054d0e43/app/routers/settings.py) · [Изменение ноды](https://github.com/PasarGuard/panel/blob/eba70d68eaa5a89e34ffebb47c8fd5ce054d0e43/app/operation/node.py) · [Изменение core](https://github.com/PasarGuard/panel/blob/eba70d68eaa5a89e34ffebb47c8fd5ce054d0e43/app/operation/core.py)

После записи независимо перечитай объект, сравни все поля до/после и проверь затронутые и контрольные профили. Если операция затрагивает ноду, сопоставь попытку `Start` в журнале панели, приём RPC на pg-node, ответ `GetBaseInfo.started`, процесс и клиентские слушатели. При тайм-ауте не повторяй запись до выяснения результата. Заверши отчёт списком фактически подтверждённых изменений и оставшихся различий.

## Если панель отправила Start, а нода его не видела

Проверяй **с хоста или сетевого пространства панели**, используя IP, семейство и управляющий порт из её записи. На Linux при наличии утилит с соответствующими опциями:

```sh
# На стороне панели, для IPv4. Переменные заполнить значениями из проверенной записи.
ip -4 route get "$NODE_IP" from "$PANEL_IP"
traceroute -n -T -s "$PANEL_IP" -p "$NODE_PORT" -q 1 -w 2 "$NODE_IP"
# На ноде проверить обратный маршрут от адреса, на который послали запрос.
ip -4 route get "$PANEL_IP" from "$NODE_IP"
```

Если запись использует прокси, IPv6 или NAT, сначала установи фактические точки и адреса; одиночная прямая IPv4-трасса описывает только выбранный путь. Для приписывания потери сравни одну попытку в общем окне UTC на обеих сторонах: выход SYN, его приход, выход ответа и получение на панели. Молчащий hop не устанавливает место потери. При установленном TCP переходи к TLS, авторизации и журналу RPC. Подробный порядок и ограничения захвата — в [сетевой инструкции](../vps-node-network-setup/references/network-evidence.md).
