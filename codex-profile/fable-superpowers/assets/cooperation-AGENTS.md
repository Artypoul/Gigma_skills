# Global working agreements

These are the user's standing workflow preferences for all Codex chats and projects. They explicitly adapt overlapping plugin defaults. Follow system/developer instructions, runtime permissions and applicable project rules; a more specific user request controls the current task.

## Roles and routing

- Use Fable 5 Codex (`fable5-codex`) as the general baseline: clear communication, evidence-based research, appropriate tools, preservation of user work and honest verification. Load its entry point and only the references relevant to the task; reuse instructions already read in the current context.
- Use Superpowers as the default engineering workflow for features, bug fixes, refactoring and code review. Apply only the skills needed for the current stage. General questions, research and document tasks use Fable plus the relevant specialist skills, without automatically starting an engineering workflow.
- Run one orchestrator per task. Do not additionally start `codex-toolkit:feature`, a second generic planning/review process or a planning-only PR merely because a skill's default trigger matches. Use another full workflow when explicitly requested by the user or required by applicable project instructions. In that case, fit compatible Superpowers techniques into that workflow. Domain skills contribute checks within the same stages.

## Load the actual skills

- Prefer the host's live enabled-skill catalogue and the exact paths it supplies. Fable's `search_skills` is an optional helper, not the authoritative list of all installed plugins. Its `limit` must be between 1 and 50. A helper error or zero matches does not establish that Superpowers is absent.
- If a required skill is missing from a helper result, use the native catalogue or `codex plugin list --json` to verify the plugin is installed and enabled. Resolve its exact marketplace, name and active version to the installed plugin manifest and read the relevant `SKILL.md` from its declared skills directory. Do not guess a version, select the newest cache directory or load disabled plugins. When discovery remains unavailable, report that specific gap instead of silently switching workflows.
- Announce a skill as used only after its instructions were actually loaded into this context and applied. A search result, an installed package, a plan to read it or an empty tool response is not activation evidence.

## One set of stages and evidence

- Read the available project context before asking questions. Reuse existing requirements, decisions, designs, plans, task tracking, workspaces and applicable review results. One artifact or completed stage satisfies equivalent requirements from Fable, Superpowers and generic workflow/quality skills.
- Keep one source of truth and one implementation plan. Create a separate design document only when complexity or project rules make it useful. Reopen completed stages only when changed scope, new evidence or a concrete unresolved finding justifies it. After compaction or handoff, recover the existing state and continue.
- Load relevant skills once per applicable context; do not recursively invoke every router or reread unchanged manuals just because several plugins mention skill discovery. Preserve required specialist instructions and load new material when the task actually needs it.
- For a fully specified mechanical edit, the Fable entry point plus the relevant validation instructions are sufficient. Do not load the large source-faithful port or broad engineering/quality manuals unless a concrete uncertainty or mandatory project rule requires them. Read task sources once with usable line numbers and paths rather than rereading them solely to format citations.

## Questions and autonomy

- Ask only when missing information materially affects correctness, scope, authorization or a consequential product decision. First check the conversation, code and available sources. Make routine reversible implementation choices yourself and briefly state material assumptions.
- A clear request to implement authorizes the normal reversible steps needed within that scope. Proceed without ritual questions about motivation, repeated design/plan approvals, execution-method selection or "shall I continue?" prompts. An existing approved specification or plan remains approved. Ask a focused question for a genuinely unresolved consequential choice; give a recommendation when useful. Honor planning-only requests and explicit approval gates.
- Deliver a blocking clarification once. Finish the available context gathering first. If a suitable input tool is available, submit the question once and keep that request pending; otherwise end the turn with one concise question. Do not ask in commentary and repeat it in the final message, continue unrelated discovery after asking, or start work whose behavior depends on the answer. Resume from the answer without restarting completed stages.
- These preferences explicitly override redundant generic brainstorming, design-approval, plan-approval and clarification defaults in skills. Preserve real permission checks, mandatory project review/CI gates and authorization boundaries for destructive, irreversible or consequential external actions; do not infer authorization for unrelated actions.

## Proportionate development

- Small, fully specified changes: inspect the relevant files, make the focused change, run proportionate validation and report. Skip separate design documents, full plans, planning PRs and new worktrees unless required by the project or user.
- Substantial development: understand the requirements, keep one concise plan, implement, verify and review. Use `brainstorming` for real uncertainty, `writing-plans` for multi-step work and `systematic-debugging` for bugs. Reuse approved material instead of repeating those stages.
- Choose `executing-plans` for cohesive work in the current context. Use `subagent-driven-development` or `dispatching-parallel-agents` when independent tasks or fresh reviews justify delegation and tools permit it. Preserve a method the user selected. Do not ask the user to choose an execution mode for routine work.
- Reuse a suitable existing checkout or worktree and preserve unrelated changes. Create isolation when requested, required by project rules or materially needed; prefer the host's native worktree tools.
- Use TDD for new behavior and reproducible bugs where the project supports meaningful tests. For prose, formatting and mechanical configuration changes, use inspection or existing validators rather than artificial new tests. These are standing exceptions to generic always-TDD and ask-before-exception defaults. Do not delete unrelated or working code merely to reenact a test-first sequence.
- Run relevant checks after the latest affecting change. Share the resulting evidence across workflows. Perform the review required for the chosen execution method; do not add an identical extra review solely to satisfy another plugin. Repeat checks/reviews when affected by later changes, failures or unresolved findings, and complete all required project checks.
- An independent review requires an actual available reviewer tool: dispatch a separate read-only reviewer, retain the returned agent/review identifier, and obtain its substantive verdict before claiming the review passed. Follow the actual tool schema rather than copying a tool name from a skill. An announcement, empty `wait`, missing receiver, timeout or self-review does not meet this condition. Record a compact receipt in the task record or `.superpowers/reviews/`: reviewer identifier, reviewed scope/revision and returned findings/verdict; preserve that receipt when cleaning temporary task tracking. A delegated reviewer does its assigned read-only pass itself and returns findings; it does not launch another reviewer or a fresh implementation workflow. When native delegation is unavailable, a separate authenticated, scoped `codex exec --ephemeral --sandbox read-only` may provide the independent review: retain the invocation, exit result and returned report. If neither capability is available, explicitly label any author pass as self-review and leave a required independent-review gate open. Never invent or infer a reviewer result.
- Finish with the concrete result, actual validation and material limitations. Keep progress updates concise and continue authorized work without repeated continuation prompts.
