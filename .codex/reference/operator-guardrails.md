# PasarGuard/VPS operator guardrails

Канонический набор правил для задач владельца о VPS, PasarGuard, pg-node, Xray, нодах, панели, firewall и подписке. Остальные VPS/Node/Panel-скиллы ссылаются на этот файл и не дублируют его текст.

## 1. Scope и карта объектов

Перед первым действием зафиксируй целевую ноду, Node ID, Core ID, Host ID, Group ID, подписку, разрешённые адреса, запреты и окно времени. Сопоставь:

`Node → Core → inbound tag → Host → Group → Subscription`

Отдельно запиши management IP/порт, SSH IP/порт, client IP/порт и egress IP. Имена не заменяют ID; IP одной ноды нельзя переносить в другую. Последнее явное решение владельца имеет приоритет только для названного объекта и среды.

## 2. Операторский режим и доступ

Для задачи владельца/оператора этот файл имеет приоритет над пользовательским onboarding и опросом вариантов. Не открывай Happ или рабочий стол и не используй пользовательский VPN как доказательство, если это не разрешено отдельно.

Используй только явно названного пользователя и ключ из ранбука. Перед SSH сверяй IP, порт, fingerprint и `known_hosts`; после входа проверяй `hostname` и `id -un`. Ошибка авторизации останавливает попытки: нельзя перебирать ключи, пользователей или root-входы.

Не переходи на другую ноду и не создавай relay, SSH-туннель, port-forwarding или прокси через другую ноду без отдельного прямого разрешения. Если разрешено несколько management-адресов, сохраняй весь allowlist и проверяй каждый адрес; не заменяй список одним IP.

Задавай только один короткий вопрос, если без ответа нельзя выбрать действие или проверить результат. Не спрашивай то, что уже есть в ранбуке, панели, скриншоте или предыдущем ответе. Не повторяй уже выданное согласие.

## 3. Read-only до записи

До любой записи сними актуальные объекты панели, Node API, live-процесс, применённый config, executable/assets path, listeners, firewall, fail2ban, логи и свежую подписку. Отдельно отметь `fact`, `hypothesis` и `unknown`; симптом (timeout, n/a, fallback, connected) не является причиной.

Для аудита, review и чекапа записи запрещены. Для согласованного ремонта подготовь таблицу:

`объект → поле → старое → новое → эффект → backup → rollback → проверка`

## 4. Сеть и внешний провайдер

Разделяй три слоя: Xray listener, firewall ОС и внешний firewall/API провайдера. Порты 62050/62051 проверяй как управление Node; 443/8443/9443/9444 — как клиентские входы. Локальный `ss`, ping, SYN, `connected` и listener не доказывают внешнюю работоспособность.

Кабинет или API провайдера запрашивай только после доказательства, что SSH, Node API, firewall ОС, fail2ban и прямой внешний TCP не объясняют отказ. Если доступа к внешнему слою нет, ставь `unknown`, а не называй блокировку найденной.

Внешнюю проверку выполняй с разрешённой внешней точки для каждого опубликованного профиля. VPN агента можно записать как отдельный путь измерения, но нельзя выдавать за клиентское доказательство.

## 5. Xray, transport и geodata

Сверяй фактические версию и SHA-256 pg-node, контейнера и Xray отдельно. Проверяй `XRAY_EXECUTABLE_PATH`, `XRAY_ASSETS_PATH`/`XRAY_LOCATION_ASSET`, реальный PID, применённый JSON и файлы внутри контейнера.

Официальные geodata принимай только после проверки источника, размера и SHA-256; затем выполняй Xray config test с теми же `geoip`/`geosite` ссылками, что используются в профиле.

`sendThrough`, transport, порты, группы, root/password/parallel access и firewall — отдельные чувствительные пакеты. Не смешивай их в одной записи и не меняй без отдельного подтверждения названного пакета.

## 6. Рестарт и запуск Core

`docker restart node` не равен запуску Core. После любого рестарта проверяй Node API, `GetBaseInfo.started`, PID Xray, listeners, логи и внешний TCP. Если Core остановлен, запускай его только согласованным способом и перечитывай состояние.

После неизвестного результата записи или timeout сначала останови мутации и сделай read-back; повторять запись вслепую запрещено.

## 7. Подписка и приёмка

Проверяй подписку до и после изменения: HTTP-код, формат, заголовок `Routing`, декодированные routing keys, число профилей и каждый затронутый профиль по address, port, transport, SNI/Host/path и routing refs.

Профиль в списке, `connected` или один успешный тест не переводят кейс в `ready`. `ready` допускается только после всех заявленных проверок; иначе используй `partial`, `blocked` или `unknown`.

После каждой записи выполняй два прохода:

1. фактический read-back и профильные/внешние тесты;
2. отдельная проверка scope, побочных эффектов, allowlist и rollback.

В отчёте разделяй локальные файлы, production-ноду, панель и внешний провайдер. Не выводи секреты, private keys, API keys и полные персональные ссылки.
