# Операторский ранбук инцидента «Твой ВПС»

Внутренний read-only сценарий для краткого массового сбоя подключения. Пользователю этот документ и внутренние адреса не пересказываются.

## Признак инцидента

Используй ранбук, если одновременно не работают несколько конфигов или в логах PasarGuard появляются `Request timed out`, `backend not initialized`, `Stream terminated: Connection lost` либо массовые переходы узлов в `BROKEN`.

## Зафиксированный пример

27 октября 2026 года узлы `DE` (`31.77.160.204`) и `DE2` (`144.31.85.186`) таймаутились с 10:17:21 до 10:25:21 UTC. В 10:25:31 появились ответы `503 backend not initialized`, а в 10:25:33 оба узла вернулись в `connected`. Узел `NL` оставался рабочим; PostgreSQL и контейнер приложения не перезапускались.

## Порядок проверки

1. **Зафиксируй время.** Запиши часовой пояс, первый `timeout`, последний `timeout`, первый успешный reconnect и длительность окна. Логи контейнеров обычно в UTC.
2. **Проверь приложение.** На хосте PasarGuard прочитай только нужное окно логов:

   ```bash
   docker logs --since '<start-utc>' --until '<end-utc>' --timestamps pasarguard-old-test \
     | grep -Ei 'DE2|DE|backend|checker|connect|disconnect|stats|stream'
   ```

   Отдельно отметь строки `Execution of job "node_health_check" skipped: maximum number of running instances reached`: это вторичный эффект зависшего health-check, а не первопричина.
3. **Сверь статусы узлов в БД.** Используй только `SELECT` внутри контейнера PostgreSQL:

   ```bash
   docker exec postgres-postgres-1 psql -U pguard_user -d pasarguard -X -P pager=off \
     -c "select id,name,address,port,api_port,status,last_status_change,message from nodes order by id;"
   ```

   Сопоставь `last_status_change` с логами. Не выводи `api_key`, токены и содержимое пользовательских подписок.
4. **Отдели PG от узлов.** Проверь, что контейнер PostgreSQL работает, а `pg_postmaster_start_time()` не менялся. Порт `5432` может быть опубликован только на `127.0.0.1`; внешний `psql` в таком случае не является проверкой доступности БД.
5. **Проверь узлы с того же хоста.** Для каждого адреса сравни `62050` и `62051` с рабочим узлом:

   ```bash
   for h in 31.77.160.204 144.31.85.186 104.143.218.48; do
     for p in 62050 62051; do
       timeout 4 bash -c "</dev/tcp/$h/$p" 2>/dev/null \
         && echo "$h:$p open" || echo "$h:$p fail"
     done
   done
   ```

   Текущий `open` не доказывает, что порт был доступен во время инцидента; сохраняй именно исторические таймстемпы из логов.
6. **Проверь ресурсы хоста.** Сними `docker ps`, `df -hT`, `free -h` и kernel-журнал за окно. OOM, I/O errors, заполненный диск или перезагрузка меняют вывод в пользу проблемы хоста.

## Как классифицировать

| Наблюдение | Вывод |
|---|---|
| DE и DE2 таймаутятся одновременно, NL остаётся connected | Сбой доступности/состояния немецкой пары или общего маршрута к ней; PG не первопричина |
| Все узлы таймаутятся, PG и приложение живы | Проверить сеть/маршрутизацию между PasarGuard и узлами |
| `pg_postmaster_start_time()` изменился или контейнер перезапускался | Рассматривать перезапуск/сбой PostgreSQL как отдельную ветку |
| Есть `backend not initialized` после серии timeout | Узел восстанавливался, а health-check увидел его до готовности; это механизм восстановления |
| Есть OOM, I/O error, заполненный диск или reboot | Проверять состояние хоста до анализа отдельных узлов |

## Эскалация

Передай Артёму:

- окно инцидента в UTC и локальном времени;
- имена и адреса затронутых узлов;
- первый/последний timeout и момент reconnect;
- точные коды `NodeAPIError`;
- состояние NL и PostgreSQL для сравнения;
- вывод ресурсов/ядра без секретов;
- что уже проверено и какие действия не выполнялись.

Попроси провайдера немецких узлов проверить сетевое окно и node-side журналы, если на PG-хосте нет OOM/I/O/reboot и только DE/DE2 были недоступны.

## Запрещённые действия без отдельного разрешения

Не выполнять `docker restart`, `docker compose up/down`, `systemctl restart`, изменения firewall/SSH/nginx, записи в PostgreSQL, сбросы узлов и изменение конфигурации. Не публиковать пароли, API-токены, приватные ключи и ссылки-подписки.

## Отдельный backup-дефект

Ошибка backup-unit `No such container: celerity-mongo` фиксируется отдельным инцидентом. Не считать её причиной падения DE/DE2 без совпадения времени и дополнительных доказательств.
