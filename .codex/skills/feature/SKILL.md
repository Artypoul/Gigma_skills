# /feature - фича от идеи до готового PR

Это skill не только для планирования: он ведёт полную разработку фичи в doc-first порядке. Сначала сделай документ-план, открой planning-only PR и дождись review-gate, затем напиши код в той же ветке/PR, проверь реализацию и доведи pull request до review-ready состояния. Пользователь мерджит в конце.

## Файлы этого скила

Пути вида `references/<файл>.md` в этом документе указывают **внутрь папки самого скила** — туда, где лежит этот `SKILL.md`, — а не внутрь репозитория задачи. Рабочая папка агента при работе по фиче почти всегда равна папке проекта, поэтому голый `references/edge-matrix.md` там не найдётся; это не признак того, что файл устарел или удалён.

Открывай их по абсолютному пути: `<абсолютная папка загруженного скила feature>/references/<файл>.md`. Если папка скила неизвестна, найди файл по имени (`edge-matrix.md`, `mandatory-plan-table.md`) в каталоге установленных скилов или плагинов — в Codex-шелле переменные окружения плагина (`PLUGIN_ROOT`, `CLAUDE_PLUGIN_ROOT`) обычно не заданы, поэтому на них не опирайся.

Файлы скила читаются, а не пересказываются по памяти: обязательная таблица плана и злой самопроход перед push держатся именно на них. Если файл действительно не открылся, скажи об этом прямо в чате и в PR, а не подменяй его собственной версией списка.

## Зачем именно так

Ошибка в дизайне дёшево чинится, пока это текст. Ошибка в готовом коде стоит дороже. Поэтому сначала зафиксируй план, проверь его, и только потом пиши код.

## Как общаться

Пользователь часто не разработчик. Пиши простым языком, короткими предложениями, без лишнего жаргона; термин при первом употреблении объясни одной строкой. В чат выноси только суть: что делаешь, что уже готово, что дальше. Технические детали держи в плане, PR и self-review.

**Язык артефактов фичи:** описание фичи, plan-doc в `docs/`, PR `Summary` и
`Test plan` пиши на русском. Английский оставляй только там, где он является
частью технического контракта: имена классов, API-полей, команд, ключей,
сообщений commit и принятых в репозитории терминов. Отступать от этого правила
можно только по явной просьбе пользователя или по более строгому локальному
правилу репозитория.

Перед стартом фичи убедись, что понятны желаемый результат и причина. Если глобальный clarification-вопрос уже задан и ответ пользователя это объясняет, используй этот ответ и не задавай второй вопрос. Иначе спроси: «Что ты хочешь сделать и почему?». После ответа кратко переформулируй цель, назови риски/развилки и предложи следующий шаг.

Если запрос, план или деплой выглядят спорно или опасно, с пользователем можно спорить, но только предметно: через факты из кода, DNS, конфигов, HTTP-ответов, логов, прав доступа, данных или продакшен-риска. Не спорь вкусом и не дави авторитетом; если уверенность ниже высокой или есть несколько нормальных продуктовых вариантов, задай конкретный уточняющий вопрос и предложи рекомендуемый вариант.

## Кто что делает

- Ты: собираешь контекст, пишешь план, пишешь код, прогоняешь проверки, разбираешь замечания.
- Плановый консилиум: 2-3 независимые review-роли помогают доработать plan-doc до кода. Роли выбирай по рискам задачи: product contract, architecture/data/migrations, API/RBAC, security, tests/maintainability, frontend UX.
- Монстры / PR-боты: Claude monster, Codex monster, `monster-reviewer`, `Codex monster review` или аналогичные ревьюеры проекта. Если они подключены, после каждого push их ревью считается частью workflow.
- Пользователь: ставит задачу, отвечает только на реальные продуктовые развилки и мерджит в конце.

## Дисциплина фаз (без механического контроллера)

Механический first-pass-контроллер отключён по решению Арта (09.08.2026): Task Lock не создаётся, `quality-control.ps1` не вызывается, «Quality state» не упоминается. Фазовая дисциплина ведётся текстом:

1. Планирование: границы фазы живут в plan-doc — scope, узкий write-scope, строки «вне scope: …», критерий готовности DoneWhen. До снятия plan review-gate production code не пишется.
2. Реализация: пиши только в утверждённый scope; тесты, линтеры и злой самопроход — до первого push (Шаг 4).
3. Публикация: перед commit/push/PR — проверки и self-review по актуальному diff; новая правка файла обнуляет прежние зелёные результаты; новый push заново открывает review.
4. Merge, force-push, deploy и любые production-записи — отдельные production-действия, каждое требует отдельного точного разрешения Арта в последней реплике. Если в конфигурации механический контроллер first-pass-quality всё же включён, production-действия авторизуются его штатным production-флоу (Task Lock + Entity Lock + свежее подтверждение) — в такой конфигурации запрет на Task Lock не действует.

Приоритет правил: прямое указание пользователя и safety-ограничения → ближайший `AGENTS.md`/локальный project skill → `$feature` → общие значения по умолчанию. Более строгий локальный gate сохраняется; конфликт нельзя «решать» ослаблением безопасности.

Не используй sub-agents автоматически только ради «консилиума». Если пользователь не просил делегирование, используй monster-review, локальные review skills или независимый ручной self-review ролями; результат делегата родитель проверяет сам.

## Поток

### Шаг 0 - Подготовка

1. Если пользователь ещё не объяснил цель и причину в уже заданном clarification-ответе, спроси: «Что ты хочешь сделать и почему?». Не дублируй вопрос.
2. Прочитай локальные правила репозитория: `AGENTS.md`, `CLAUDE.md`, `.claude/skills/`, `.codex/skills/`, `README` и соседние документы. Канон репозитория важнее общих привычек.
3. Быстро собери контекст по затронутым модулям, тестам, данным, API и пользовательскому сценарию.
4. Определи базовую ветку по правилам проекта. Если явного правила нет, опирайся на текущий git flow.
5. Создай ветку `feature/<short-name>`, если проект не требует другой схемы именования. Новая фича = отдельная ветка и отдельный PR по умолчанию: не прицепляй её к чужому или уже открытому PR, даже если он кажется близким по смыслу. Объединять можно только по явной просьбе пользователя.
6. До первой planning-правки зафиксируй границы фазы словами (в чате и затем в plan-doc): scope, write-scope, «вне scope: …», DoneWhen.
7. Зафиксируй один independently deliverable результат и один основной PR. Если по ходу появляется второй результат, который можно независимо мержить или откатывать, останови новые записи, сделай короткий handoff и предложи отдельную задачу/PR. Продолжай всё вместе только после явного выбора пользователя.
8. Если задача на самом деле маленькая и безопасная, не используй этот skill: просто сделай правку.

Всегда полный флоу с планом: план → ревью → код → ревью. Что достойно отдельной фичи, определяет пользователь и локальные правила репозитория; совсем мелкие безопасные правки делаются вне этого skill.

### Шаг 1 - План-документ

1. Напиши короткий план в `docs/plan-<feature>.md` или в той папке, которую предпочитает репозиторий. Держи его компактным: обязательная таблица плюс короткие списки, ориентир — одна экранная страница. Разжёванные абзацы, пересказ кода и повтор одного и того же разными словами — не «тщательность», а мусор: подробности живут в коде, PR и self-review.
2. Перед написанием plan-doc прочитай `references/mandatory-plan-table.md` (файл лежит в папке скила, см. «Файлы этого скила») и добавь в план обязательную таблицу `Что делаем` с колонками: `Что делаем`, `Было`, `Стало`, `Как делаем`, `БД`, `Endpoint / команда`. Таблица обязательна для каждого plan-doc; если пункт не применим, явно пиши `БД не меняется`, `новых полей нет`, `без endpoint` или `команда не нужна`.
3. Зафиксируй в плане:
   - что делаем и зачем;
   - что входит и не входит в scope;
   - **что пользователь запретил трогать** — отдельной строкой `вне scope: …` по каждому явному запрету из диалога, чтобы он пережил сжатие контекста и не был отменён чек-листом ревью;
   - какие файлы, модули, эндпоинты, таблицы или экраны трогаем;
   - обязательную таблицу `Что делаем` из `references/mandatory-plan-table.md`: каждая строка показывает действие, `Было`, `Стало`, технический способ, изменения БД и endpoint/команду; названия полей, статусов, событий, команд и endpoints должны быть понятны владельцу продукта без чтения кода;
   - **что будет в БД — обязательно схемой:** если БД меняется или фича хранит/читает новые данные, покажи таблицы, новые/изменённые поля, индексы, связи, где лежат токены/секреты, пример строки данных и что намеренно НЕ создаётся. Если БД не трогаем, прямо напиши `БД не меняется`. Формат — markdown-таблица, Mermaid ERD или короткий блок `таблица -> поля -> связи`;
   - **что переиспользуем (проверено по коду) — НЕ изобретай заново:** до проектирования новой таблицы/сервиса/эндпоинта прогрепай репозиторий на дубли. Логика — есть ли сервис/команда/джоба/контроллер, который уже делает похожее. Таблицы и поля — есть ли таблица/колонки, где данные уже живут (миграции, `$fillable`, поля «внешних ID» типа `provider_id`/`provider_code`, `*_integrations` + параметры). Нашёл — реюз/расширяем, не пиши параллель; по каждому решение «реюз / расширяем / новое — почему»;
   - edge cases по `references/edge-matrix.md`: строка в плане по каждому применимому пункту, неприменимые — явно «не применимо, потому что …»; плюс риски и совместимость;
   - если фича читает/пишет данные внешнего API — откуда взят настоящий контракт (curl к реальному серверу, тест бэкенда или донор), а не «по памяти»;
   - как будет проверяться результат.
4. Сразу после первого draft plan-doc собери плановый консилиум на доработку документа. Минимум 2-3 роли по рискам задачи; используй monster-review, локальные project skills или ручной self-review ролями. Sub-agents допустимы только когда пользователь или более приоритетная активная инструкция явно разрешили делегирование.
5. Внеси реальные замечания консилиума в plan-doc до открытия/обновления planning PR. В плане или PR body явно укажи: какие роли смотрели план, какие блокеры/риски нашли, что исправлено, что осталось продуктовым вопросом.
6. Если в репозитории уже есть шаблоны планов или локальные skills вроде `backend-plan` или `frontend-plan`, используй их вместо собственного формата. Для backend/API-фичи, затрагивающей контракты, инварианты, права, деньги, лимиты, транзакции, идемпотентность, миграции или события, слот `backend-plan` закрывает скил `ddd-api-standard` из плагина `backend-workflow`, когда он установлен. Если его нет, используй доступный project-local `backend-plan` или базовый формат этого скила и явно отметь отсутствие специализированного backend-review; не имитируй недоступный скил.
7. Как только план-документ и первый плановый консилиум готовы, создай commit, сделай push и открой PR сразу как `ready for review`, не `draft`. На старте в PR должен быть только план-документ или минимальный набор файлов, нужный для обсуждения плана.
8. В `PR body` явно напиши, что это planning-only раунд: в этом PR сейчас только план, реализации пока нет, код пойдёт после апрува плана. Не полагайся только на комментарий в таймлайне: ревьюеры и боты должны увидеть это прямо в описании PR.
9. Оформляй этот первый `PR body` в явном формате с разделами `Summary` и `Test plan`.
10. В `Summary` кратко перечисли scope плана, ключевые решения текущего раунда и результат планового консилиума.
11. В `Test plan` укажи `not run (planning document only)`, если в PR пока только документация и проверять ещё нечего.
12. Не затирай уже существующие записи в PR без явной причины. Если нужно обновить `PR body`, правь его узко и сохраняй уже добавленные человеком или агентом секции, заметки и контекст. Предпочитай дописывать новый статус или новый блок, а не переписывать всё описание с нуля.
13. Не удаляй историю обсуждения: не компенсируй новый контекст массовой перезаписью комментариев, не скрывай прошлые договорённости и не стирай старые summary, если они всё ещё полезны для ревью.
14. Делай коммиты последовательно и прозрачно: каждый заметный шаг, правка по ревью или переход план -> код должен идти новым commit'ом с понятным сообщением.
15. Не используй `git commit --amend`, rebase с переписыванием опубликованной истории или force-push в feature workflow, если пользователь этого прямо не попросил.
16. Если задача упирается в реальное продуктовое решение пользователя, остановись после плана и спроси только про этот узкий выбор. Иначе переходи дальше без паузы.
17. Сразу после открытия planning-only PR считай, что включён review-gate: до его снятия нельзя писать production code. Разрешены только правки plan-doc, PR body и ответы на замечания к плану.
18. После создания PR сразу пришли пользователю полную ссылку на PR. После каждого последующего push/update этого PR снова укажи ссылку в ближайшем статусе или финальном сообщении.

После успешного push watch-hook только ставит pending-маркер; он не читает GitHub и не является поллером. Сам агент или реальный monitor должен проверять ревью через GitHub/CLI и inbox до снятия review-gate.

### Шаг 2 - Проверка плана

1. Проверь план на дыры до написания кода: права доступа, пустые состояния, миграции, ошибки, откат, наблюдаемость, тесты.
2. Проведи или обнови плановый консилиум по опубликованному plan-doc. Если план менялся после замечаний, консилиум должен смотреть свежую версию, а не старый draft.
3. Если в проекте есть автоматическое ревью PR, PR-боты или monster-пайплайн, используй их. Для plan-only PR обязательно дождись Claude monster и Codex monster / `monster-reviewer` и `Codex monster review`, если они подключены в проекте. Их копии часто приходят в `$HOME/.claude-bot-inbox/<owner>-<repo>-pr<N>.md`.
4. Пока не получен сигнал review-gate, не пиши код фичи, не меняй тесты под реализацию и не начинай implementation commits. На этом этапе разрешены только правки плана, PR body и review-related updates.
5. Исправь блокирующие замечания в плане в том же PR отдельными понятными commit'ами, не затирая уже опубликованную историю без прямой команды пользователя.
6. После исправления блокеров плана обнови вывод планового консилиума: что было найдено, что исправлено, какие риски остались и почему они не блокируют код.
7. Считай review-gate снятым только если выполнено одно из условий:
   - пользователь явно написал, что план одобрен и можно идти в код;
   - плановый консилиум и `monster-reviewer` / `Codex monster review` отработали, и по их замечаниям не осталось блокеров;
   - пользователь явно разрешил не ждать внешнее ревью.
8. Если есть неоднозначность между «не затягивай» и «ждать ревью», всегда выбирай ожидание ревью.
9. Если после 4 кругов ревью по плану блокеры не заканчиваются, остановись и коротко позови пользователя.

Чини все реальные замечания P1/P2/P3, кроме вкусовщины и вопросов, где нужно решение владельца продукта. Вердикт «блокеров нет», «можно мержить», «Swish» или «no major issues» завершает цикл; не запускай бесконечные дополнительные круги «на всякий случай».

### Шаг 2.5 - Wait For Review Gate

1. После создания planning-only PR остановись и дождись review-cycle по плану.
2. Сначала проверь плановый консилиум, затем `monster-reviewer`, затем `Codex monster review`, затем остальные PR comments/reviews, если они есть.
3. Пока review-gate не снят, делай polling статуса ревью каждые 30 секунд. Проверяй `monster-reviewer`, `Codex monster review`, review comments, reviews и обычные comments в PR.
4. Если ревью пришло, разбирай только замечания к плану и обновляй только документ, PR body и planning commits.
5. Если ревью ещё не пришло, не начинай код без явного разрешения пользователя или явного правила проекта, что ждать не нужно.
6. При любом сомнении выбери более строгий режим: ждать review-gate, а не переходить к реализации.

### Шаг 3 - Переход план -> код

Как только по плану нет блокеров И review-gate снят, отметь это одной строкой в plan-doc или PR и начинай реализацию сам, без лишней паузы и без нового запроса. План остаётся в PR как рабочее ТЗ, по которому потом сверяют реализацию.

### Шаг 4 - Реализация

1. Реализуй фичу строго по утверждённому плану в той же ветке.
2. **Контракт с натуры.** Если код читает или пишет данные внешнего API/чужого сервиса: сначала получи настоящий ответ (curl к реальному серверу, тест бэкенда или код донора) и сохрани в тесты образец (фикстуру) с **реальной структурой, но обезличенным содержимым**: токены, секреты, телефоны, email и персональные данные замени плейсхолдерами, лишние поля сократи. Сырые ответы живых пользователей в репозиторий не коммитятся. Разбор формата «по памяти» запрещён. Для починки дефекта — сначала красный тест, доказывающий проблему на старом коде, потом фикс.
3. Следуй существующим паттернам проекта и переиспользуй локальные helper'ы, тестовые утилиты и инфраструктуру.
4. Держи изменения сфокусированными на задаче.
5. Доводи фичу до production-ready состояния: закрой основные состояния, ошибки, пустые случаи и совместимость.
6. **Перед первым push с кодом** прогони проверки строго после последней содержательной записи и в таком порядке: formatter/fix → целевые тесты → злой самопроход по `references/edge-matrix.md` → полный применимый suite → `git diff --check` и финальное чтение diff. Если formatter или любой следующий шаг изменил файл, все затронутые проверки после него устарели и запускаются заново. Цель: внешний ревьюер находит в первом раунде не больше 1–2 замечаний.
7. **Reviewer-capacity gate.** До первого code-push используй точный preflight обязательного reviewer, если проект предоставляет такой скрипт или команду. Не имитируй отсутствующий анализатор эвристикой. Если точного preflight нет, заранее раздели independently deliverable schema/migration, API/runtime и UI-транши, когда один diff объединяет несколько таких слоёв. Технический отказ reviewer вида `too large`, `too many targeted symbols` или эквивалент — blocker: не подменяй его локальным ревью и не называй PR готовым; раздели diff или запроси продуктовое решение, если разделение меняет контракт/rollout.
8. Для гарантий, зависящих от PostgreSQL, миграций, triggers/functions или конкурентности, проверка на другой СУБД/моках не закрывает gate. Если exact-engine runner доступен только в CI, сначала опубликуй минимальный проверяемый migration/schema tranche, дождись его результата и только затем наращивай зависимый API/runtime-код. Skipped exact-engine tests означают `partial`, а не `ready`.
9. Commit -> push.
10. После каждого push с кодом обязательно отпишись в самом PR комментарием: что изменено, какие проверки прошли, что ещё красное/ожидает, и нужен ли новый review. Не ограничивайся только сообщением в чат.
11. После push напомни пользователю полную ссылку на текущий PR, чтобы он не искал её в истории чата.

### Шаг 5 - Проверка кода

1. Подтверди, что formatter/fix, целевые тесты, edge-review, полный применимый suite, `git diff --check` и финальное чтение diff выполнены именно после последней содержательной записи. Не запускай полный suite до formatter, если formatter может менять файлы.
2. Просмотри diff как ревьюер: ищи баги, регрессии, пропущенные состояния, лишний scope и неясные названия.
3. После реализации и локальных проверок собери консилиум по фиче: минимум 2-3 независимых review-роли по рискам задачи (например API/RBAC, product contract, tests/maintainability, frontend UX, security). По умолчанию используй monster-review, локальные review skills или ручной self-review; sub-agents — только при разрешённом делегировании. Вывод должен быть разобран до финала.
4. Если monster-review, консилиум или другой reviewer нашёл блокеры или реальные P1/P2/P3 — исправь их в той же ветке/PR, снова прогони релевантные проверки, сделай push и повторно пришли пользователю ссылку на PR.
5. После каждого исправления по review обязательно заново запусти консилиум/re-review по текущему diff. Нельзя считать PR готовым, если последний консилиум смотрел старый diff, plan-only состояние или код до починки.
6. Если внешний monster-review, Codex review или Claude review завис, недоступен или упёрся в лимиты, не подменяй это молчаливым "готово": явно скажи о недоступности и запусти локальный консилиум ролями по актуальному diff.
7. Если в проекте есть внешний цикл ревью, дождись замечаний и разбери их до состояния без блокеров.
8. Повторяй цикл fix -> push -> re-review -> consilium, пока блокеров не останется, и сохраняй историю последовательными commit'ами вместо переписывания уже опубликованной ветки.
9. **Ревью-в-правило.** Если внешний ревьюер нашёл класс ошибки, который мог быть пойман локально по `references/edge-matrix.md`, — закрепи его правилом, не смешивая репозитории: работаешь в самом каталоге скилов — добавь строку в edge-matrix тем же PR; работаешь в продуктовом репо — добавь строку в локальный чек-лист проекта (project skill / `AGENTS.md`) в текущем PR, а пополнение глобальной edge-matrix предложи пользователю отдельным follow-up в каталоге скилов. Файлы установленного плагина из продуктового PR не правятся. Каждый класс ошибки внешнее ревью должно находить максимум один раз.
10. Если прошло 4 круга, а блокеры продолжают возвращаться, остановись и коротко опиши пользователю, что осталось.

«Бот сказал OK» — это финал review-цикла, а не предварительный кивок. Не догоняй бесконечные мелочи после снятия блокеров, если они не меняют production-риск.

### Шаг 6 - Финал

1. Если в репозитории есть `/pr-finalize` или аналогичный локальный workflow, прогони его: человеческое описание PR, сценарии «до/после», тест-план, HISTORY/журнал, self-review.
2. Подготовь понятное summary для PR или пользователя: что изменилось, что теперь работает иначе, как это проверено.
3. Если workflow проекта предполагает PR, собери review-ready описание без кода и с понятными сценариями проверки.
4. Сообщи пользователю, что задача готова к мерджу, и дай полную ссылку на PR, если она есть.
5. Не мержи без прямой команды пользователя.

### Шаг 7 - После мерджа

Если пользователь пишет `смержил`, `смерджил`, `merged` или явно говорит, что PR уже влит:

1. Проверь, что PR действительно merged в целевую ветку и что локальный/remote `master` видит нужный merge commit.
2. Если в репозитории настроен автодеплой от merge — дождись его завершения и проверь живой продакшен (hash сборки, видимый признак фичи или целевой запрос) до любого отчёта «готово на сайте». «Смерджено + CI зелёный» ≠ «опубликовано»; если прод не обновился — скажи прямо и найди причину.
3. Сделай production sanity-check: нет ли явных красных блокеров, которые прямо делают деплой опасным. Если риск критический и подтверждённый, остановись и коротко объясни.
4. Слова `смержил`/`merged` подтверждают только факт merge и никогда сами по себе не разрешают deploy. Подготовь точный deploy-путь, целевой environment и commit, затем попроси отдельное явное подтверждение, если последняя реплика пользователя уже не содержит недвусмысленного разрешения на этот конкретный deploy.
5. После отдельного подтверждения выполни ровно один deploy-вызов. Предпочитай типизированный проектный wrapper (workflow/скрипт деплоя репозитория). Raw SSH/shell — только если Арт явно разрешил его в последней реплике для этой конкретной задачи, и тогда разрешение привязано к точно названным цели, среде и семейству команд, действует одноразово и истекает при любом отклонении, смене scope или неизвестном исходе; при неизвестном исходе не повторяй вслепую.
6. После успешного deploy запусти end-to-end проверку: проверь живой API/основной пользовательский сценарий фичи на указанном production или staging-пути.
7. В финале коротко напиши: какой commit задеплоен, как прошёл deploy, какие e2e-проверки выполнены и что осталось красным/непроверенным. Не называй deploy успешным при unknown outcome.

## Стоп-кран

Пользователь главнее workflow. Если пользователь пишет «стоп», «оставь», «не туда», `pause` или `stop`, остановись немедленно, не пытайся «дочинить круг». Правила держат агента, не пользователя.

Запрет пользователя («это не трогаем», «модуль X ни при чём», «не лезь туда») действует до конца задачи, а не до конца текущего шага. Занеси его в план строкой `вне scope: …` и перечитывай после каждого сжатия контекста. Чек-лист скилла или ревью не отменяет запрет: помечай такой пункт «не проверяем по решению владельца» и иди дальше, не возвращая запрещённое в выводы.

## Рельсы feature workflow

Механических рельсов нет: first-pass-контроллер и глобальные feature-hooks (watch/turnstile) отключены 09.08.2026. Review-цикл держится правилами: после каждого push сам проверяй ревью (GitHub/CLI и inbox `$HOME/.claude-bot-inbox/<owner>-<repo>-pr<N>.md`), чини блокеры в той же ветке и не объявляй PR готовым, пока обязательное ревью не завершилось на актуальном commit. Кап — 4 круга (см. глобальный AGENTS.md).

## Чеклист плана

- Что меняется для пользователя или системы.
- Обязательная таблица `Что делаем` из `references/mandatory-plan-table.md`: `Что делаем`, `Было`, `Стало`, `Как делаем`, `БД`, `Endpoint / команда`; названия понятны владельцу продукта без чтения кода.
- Что пользователь запретил трогать — строками `вне scope: …`.
- Что уже есть в коде и переиспользуется (логика и таблицы), чтобы не дублировать.
- Что будет в БД: схема таблиц/полей/связей, пример строки, индексы, токены/секреты, и явное `БД не меняется`, если данных не касаемся.
- Какие части кода и данных будут затронуты.
- Какие состояния, ошибки и edge cases надо закрыть — по `references/edge-matrix.md`, применимые пункты строками в плане.
- Откуда взят настоящий контракт внешних данных (curl / тест бэкенда / донор), если фича их касается.
- Какие проверки докажут, что всё работает.
- Какие вопросы ещё реально блокируют реализацию.
- Какие роли планового консилиума проверили документ, какие замечания были исправлены, и почему оставшиеся риски не блокируют переход к коду.

## Правила выбора

- Предпочитай этот skill для нетривиальных, многосоставных или рискованных задач.
- Предпочитай короткий план перед кодом, если меняется API, UI, схема данных, фоновые процессы или несколько подсистем сразу.
- Если локальные инструкции проекта строже этого global skill, следуй локальным инструкциям.
- Если пользователь просит пропустить план, соглашайся только для простых задач. Для сложных задач всё равно сделай короткий план, но не растягивай его.
