# Edge-matrix — злой самопроход перед первым push

Цель: внешний ревьюер (monster/Codex/Claude) находит в первом раунде не больше 1–2 замечаний. Всё, что ловится этим списком, чинится ДО первого push.

## Как применять

- **В плане (Шаг 1):** по каждому применимому пункту — строка в плане; неприменимые пункты помечай явно: «не применимо, потому что …».
- **Перед первым push (Шаг 4):** пройди список по актуальному diff в режиме «злого ревьюера». Задача — не «убедиться, что работает», а «сломать».
- **В self-review:** каждый пункт — либо ✅ с анкором (имя теста/файла), либо «не применимо, потому что …». Голое «всё хорошо» не считается.

## Данные и API (backend)

1. **Data loss** — может ли update случайно стереть старые данные?
2. **Partial payload** — что будет, если придёт только одно поле из формы?
3. **null vs omitted** — различаются ли «поле не пришло» и «поле пришло null»? Для PUT явно выбери: full-replace или patch-like (для форм профиля безопаснее patch-like: не пришло → не трогаем, null → осознанная очистка).
4. **Middleware** — какие висят на route group / global и могут изменить request до валидации? (route-level `withoutMiddleware` не отменяет global.)
5. **Special values** — 0, false, "", null, [], {} в payload проверены? Falsy-фильтр их не теряет?
6. **Multi-tenant** — нет доступа к чужому project_id / counterparty_id / application_id? Есть тест на изоляцию?
7. **Authorization** — 401 (нет входа) / 403 (нет прав) / 422 (бизнес-отказ) разделены и протестированы?
8. **Race / транзакции** — lock на нужной строке; внешние вызовы после commit; при неизвестном исходе операции нет слепого повтора; идемпотентность создающих операций.
9. **Обратная совместимость** — старый фронт / legacy endpoints / старые проекты не ломаются; миграции аддитивные (nullable, без drop/rename).
10. **Тест на потерю данных** — есть тест именно на тот сценарий, где данные могут потеряться или исказиться.
11. **Legacy/null policy** — старые строки без нового поля, expiry, связи или статуса имеют явное поведение; fallback не превращает бессрочные/неполные записи в вечно активные и не ломает чтение.
12. **Rollback и cleanup** — ошибка после промежуточной записи откатывает весь use case; heartbeat/служебная запись не отменяет терминальный статус; delete/revoke закрывает связанные активные сущности с точной причиной.
13. **Порядок блокировок** — все конкурентные пути берут строки/locks в одном документированном порядке; есть параллельный тест на race/deadlock, а retry запускает весь use case в новой транзакции.
14. **Временные инварианты** — `ended_at >= started_at`, expiry не раньше создания, timestamps монотонны относительно доменного перехода; boundary/equal-time сценарии протестированы.
15. **Migration dependency inventory** — при rename/move/`SET SCHEMA` перечислены и обновлены FK, indexes, views/materialized views, triggers, trigger functions, policies, grants, defaults/sequences и ORM/raw-SQL schema qualifiers. Проверка идёт на целевом PostgreSQL, не только на SQLite/моках.
16. **Upgrade + новые данные + downgrade/forward-fix** — проверен сценарий upgrade → запись данных в новом формате → downgrade. Если безопасный downgrade невозможен, он явно блокируется и описан rehearsal/forward-fix plan без ложного destructive rollback.

## Контракт с внешним API («контракт с натуры»)

17. **Настоящий ответ получен и сохранён**: curl к реальному серверу, тест бэкенда или код донора; в тестах лежит фикстура с реальной структурой и **обезличенным содержимым** (токены/секреты/телефоны/email — плейсхолдеры; сырые данные живых пользователей не коммитятся). Писать разбор формата «по памяти» запрещено.
18. **Красный тест до фикса**: тест сначала доказывает дефект на старом коде, потом код чинится.
19. **Неизвестный статус/поле** — поведение fail-closed и видимое пользователю («статус уточняется»), а не тихое «данных нет».
20. **Сбой источника** (404 / 5xx / таймаут / рассинхрон каталога) — отдельная ветка с честной ошибкой, не маскируется под пустой результат.

## Frontend

21. **Что уже есть** — routes / components / API-клиент проверены, дубликаты не плодятся, существующий визуальный паттерн переиспользован.
22. **Состояния экрана** — loading / empty (`exists: false` — не ошибка!) / error / 401 / 403 / 422, каждое по-своему.
23. **Два пользователя** — новый без данных и старый с заполненными данными: оба сценария проходят.
24. **Payload safety** — undefined → поле не трогаем; null → осознанная очистка; 0 / false / "" — валидные значения, не теряются.
25. **Desktop и mobile** — оба экрана обновлены и показывают одно и то же состояние.
26. **Ссылки и redirect** — только http(s); внешние значения не попадают в `javascript:` / `data:`.
27. **Обязательные поля контракта** — у каждого обязательного поля запроса есть определённый источник в payload: ввод пользователя, авторизованный контекст, route-параметр или генерируемое значение (например, idempotency key). Ввод в форме обязателен только для значений, которые должен дать пользователь; пользовательское обязательное поле без ввода = блокер, а системные поля в UI не выставляются. Обратно: форма не отправляет полей, которых нет в контракте.

## Финальный вопрос

«Если ревьюер заставит это исправить — исправь до push».

## Ревью-в-правило

Если внешний ревьюер всё же нашёл класс ошибки, который мог быть пойман этим списком, — закрепи его правилом, не смешивая репозитории: в каталоге скилов — строка сюда тем же PR; в продуктовом репо — строка в локальный чек-лист проекта в текущем PR, а пополнение этого файла — отдельным follow-up в каталоге скилов. Каждый класс ошибки внешнее ревью должно находить максимум один раз.
