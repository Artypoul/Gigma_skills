# Маршрут и TCP-доказательства

## От краткого теста к локализации

Составь для проблемной и контрольной нод матрицу: клиентская сеть → вход ноды, панель → управление и вход ноды, нода → REALITY target, нода → конечный сайт. На каждом участке раздели DNS, TCP, TLS/REALITY, HTTP, передачу данных. Ограничь число попыток и объём; выводи n/N и окно времени. Сначала повтори измерение, которое отличает гипотезы, а не всю возможную диагностику.

NextTrace/NTR полезен для IP-пути, TCP/ICMP-проб и сравнения путей. Версию, доступные методы, интерфейс/source и отключение сторонней геолокации уточняй в локальном `--help`. Не передавай частные адреса/подписки геолокационным сервисам. Источник установки — официальный [NTrace-core](https://github.com/nxtrace/NTrace-core), а не случайный download mirror. Бесплатность, лицензию и драйверные требования сверяй для выбранной версии, не выводи их из названия инструмента.

Проверку до реального сайта проводи через аутентифицированный VPN-клиент, например через временный локальный SOCKS с правильной DNS-семантикой. `socks5h` передаёт DNS прокси, `socks5` может разрешать имя локально; это разные эксперименты. Публичный сертификат сайта проверяй обычным trust store. Дополняй небольшой запрос ограниченной загрузкой; latency-test приложения может пользоваться иным URL/timeout/XMUX.

Открытый TCP-порт не означает, что весь ClientHello дошёл. Успех через relay доказывает различие путей при сохранённых параметрах, но не сам по себе вину промежуточного провайдера. Меняя только путь, сохраняй цель REALITY, SNI, профиль и сайт. Учитывай, что relay меняет исходный IP и возможные политики сервера.

## Синхронные текстовые захваты

Используй доступ на обоих концах конкретного участка. До запуска проверь часы, интерфейсы, NAT-адреса и выбранный flow tuple. При NAT сопоставь отображение портов; приложенный анализатор требует одинаковых IPv4 tuple в обоих файлах. Для туннелированного маршрута захватывай один и тот же внешний или внутренний TCP-поток на обеих сторонах.

На каждом конце запускай ограниченный tcpdump до начала нового диагностического соединения. Например, после задания проверенных значений `CAPTURE_IFACE`, `SOURCE_IP`, `TARGET_IP`, `TARGET_PORT`, `CAPTURE_FILE`:

```sh
timeout --signal=INT 25s tcpdump -i "$CAPTURE_IFACE" -nn -tt -S -v -s 96 -c 400 \
  "tcp and host $SOURCE_IP and host $TARGET_IP and port $TARGET_PORT" \
  > "$CAPTURE_FILE" 2>&1
```

Здесь сохраняется текст заголовков/счётчиков. Не добавляй `-A`, `-X` или `-w`: они сохраняют payload или сырой pcap. Snaplen 96 ограничивает захват, но сам по себе не является гарантией отсутствия первых байт payload в памяти; защита сохраняемого артефакта достигается текстовым выводом без декодирования содержимого. Проверь `[|tcp]` и другие признаки усечения заголовков. Отсутствующие поля не восстанавливай догадкой. Команда может завершиться кодом timeout — нужны нормальное завершение tcpdump по SIGINT и финальная статистика, а не только exit code.

Запусти новую реальную попытку, сохрани время, source port и результат клиента. Дай завершиться повторам/ответам в общем окне; не обрывай при первом SYN. Заверши только свой сборщик так, чтобы он напечатал число captured/received/dropped. Нулевые kernel drops необходимы для сильного сравнения, но не исключают потери NIC, другое место захвата или выход за окно.

## Автономное сравнение

Скрипт `scripts/compare_tcp_sequences.py` читает два текстовых файла tcpdump с **абсолютными** seq (`-S`), IPv4, один серверный порт, только направление инициатор → сервер. Никаких сетевых вызовов или зависимостей Python вне stdlib.

```sh
python scripts/compare_tcp_sequences.py sender.txt receiver.txt \
  --source 192.0.2.10 --target 198.51.100.20 --port 443 \
  --output comparison.json
```

Вызывай по абсолютному пути к скрипту из установленного скилла либо из его каталога. Документационные IP выше — placeholders, не реальные цели теста.

Он объединяет пересекающиеся seq-интервалы, вычитает их множества, учитывает повторы, выводит ACK/SACK и число payload records. Разная пакетизация с теми же уникальными байтами не считается потерей. Проверяет SYN в обоих файлах, смену ISN на одном source port, длины диапазонов, kernel drops и ненулевые interface drops, неожиданные байты только на получателе и неподдерживаемые диапазоны/усечения. TCP sequence wrap, большие потоки (span от 2^31), TFO/payload с SYN и неоднозначные записи не интерпретирует как доказательство. Payload с FIN учитывается по seq и length, сам FIN в число байтов данных не входит.

Если в захват попали старые соединения, задавай `--source-port 50000` для известного нового тестового потока; флаг можно повторять. Запрошенный, но отсутствующий порт выводится отдельно с `selected_flow_not_found`, общий результат — `inconclusive`. Не исключай неуспешные попытки ради улучшения результата: выбранные порты и причины отбора должны соответствовать журналу теста. Без отбора неполные старые потоки будут отмечены отдельно и могут сделать общий статус `inconclusive`.

Статусы:

- `same_observed_bytes`: множества отправленных и принятых байтов совпали в этих файлах. Это не проверка успешного HTTPS/VPN.
- `observed_gap`: в окне на получателе отсутствуют некоторые наблюдавшиеся у отправителя диапазоны, ACK/SACK в обоих захватах не подтверждают их получение, базовые проверки захватов пройдены. Это **кандидат** на сетевую потерю; время/интерфейс/полноту окна проверяет оператор.
- `inconclusive`: неполные/неоднозначные данные, capture drops, некорректные ACK/SACK либо подтверждения противоречат предполагаемому пропуску. Повторить корректный захват, не обвинять сеть.

Код выхода 0 означает успешный разбор, а не здоровую сеть. Общий JSON содержит предупреждения и статус каждого потока; читай их до вывода. Обнаруженные секции с ненулевыми или отсутствующими counters делают сравнение неубедительным. Не склеивай несколько сессий tcpdump в один файл.

Для сильного вывода сопоставь отсутствующий диапазон с ACK/SACK получателя, видимыми на любом из концов, повторными отправками, тайм-аутом реального клиента и успешным контрольным потоком. Если ACK проходит дальше «пропуска» или SACK перекрывает отсутствующие в файле байты, запись не доказывает их непоступление на сервер. SACK сообщает о принятых блоках, но не гарантирует их последующее сохранение или доставку приложению: [RFC 2018, раздел 3](https://www.rfc-editor.org/rfc/rfc2018.html#section-3). Не трактуй SACK как успешный HTTPS. Выходной checksum offload и GRO/GSO не исправляй по одному сообщению tcpdump.

Проверь границы окна каждого выбранного потока. Лимит `-c 400` может завершить один сборщик раньше другого; такая обрезка не является доказательством потери. Если результат не помещается в общее окно, повтори узко отфильтрованный ограниченный захват.

После смены сборки, SNI, адреса, MTU или маршрута снимай новую пару. Указывай границу захватов: «между интерфейсами A и B»; для точного хопа нужны дополнительные точки/данные оператора. MTU/PMTUD, NAT, NIC/виртуальная сеть, фильтрация — отдельные проверяемые гипотезы, а не синонимы тайм-аута.
